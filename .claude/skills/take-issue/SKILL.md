# Взять задачу в работу

Путь одной задачи от issue до PR. Он одинаков для всех задач, и смысл скилла в том, чтобы не воспроизводить его по памяти: каждый пропущенный шаг здесь уже однажды стоил переделки.

Правила, которые действуют всегда, лежат в `CLAUDE.md`. Здесь — порядок действий.

## 1. Понять задачу

Прочитай задачу целиком: `gh issue view <номер>`.

**Зависимости.** В разделе «Зависимости» перечислены номера задач. Проверь каждую: `gh issue view <n> --json state -q .state`. Если зависимость открыта, остановись и скажи пользователю, что именно не готово. Исключение — пользователь прямо сказал делать вопреки порядку; тогда запиши это в описании PR.

**Документы.** Критерии приёмки ссылаются на документы, но не пересказывают их. Прочитай разделы по теме задачи до того, как писать код:

| Тема задачи | Что читать |
|---|---|
| Права, данные, загрузка набора, база | `docs/architecture/ARCHITECTURE.md`: «Хранение», «Права» |
| Заявки, подтверждение, заглушка ТОиР | `ARCHITECTURE.md`: «Запись» |
| Ход, бюджет, токены, `prefix_hash` | `ARCHITECTURE.md`: «Ход»; `docs/architecture/AGENT.md` |
| Инструменты, формат ответа, промпт | `AGENT.md` |
| Поиск по документам | `ARCHITECTURE.md`: «Документы и поиск»; `docs/architecture/RETRIEVAL.md` |
| Генератор данных, формат набора | `docs/business/TASK.md`: «Данные» |
| Тесты | `docs/development/TESTING.md` |
| Прогон, метрики, мутанты, судья | `docs/development/AI_TESTING.md` |
| Запуск, compose, стенд | `ARCHITECTURE.md`: «Запуск»; `docs/architecture/INFRASTRUCTURE.md`; `docs/development/STAND.md` |

При расхождении документов с заданием прав `docs/business/TASK.md`. Заметил расхождение — скажи пользователю до начала работы, а не в описании PR.

## 2. Ветка и рабочая копия

```
.claude/skills/take-issue/scripts/start.sh <номер> <тип> <кратко>
```

Тип — `feat`, `fix`, `docs` или `infra`; «кратко» — два-четыре слова латиницей через дефис. Скрипт обновляет `origin/main`, создаёт ветку `<тип>/<номер>-<кратко>` в отдельной рабочей копии рядом с репозиторием и подключает `.env` ссылкой на файл основного каталога.

Дальше работай только в этой рабочей копии. Основной каталог остаётся на `main`: в нём не правят и не коммитят.

`.env` подключён ссылкой, а не скопирован, намеренно: секреты существуют в одном месте, и правка в одной копии не расходится с другой.

## 3. Сделать

Критерии приёмки — это определение готовности. Иди по ним, а не по ощущению завершённости.

- **Тесты пишутся вместе с кодом.** У каждой строки таблиц гарантий в `ARCHITECTURE.md` есть тест с тем же названием; меняешь поведение — меняешь и таблицу, и тест в этом же PR.
- **Расхождение кода с документом не оставляй.** Если по ходу выяснилось, что документ неправ, исправь документ здесь же и напиши об этом в PR.
- **Проверяй запуском, а не чтением.** Конфигурация, написанная по справочнику, и скрипт, прошедший проверку синтаксиса, ещё ничего не доказывают. То, что зависит от случая — первая настройка, сеть, порядок старта, — запусти дважды: один удачный прогон уже однажды оказался везением.
- **Платные действия — только после подтверждения пользователя:** создание серверов и любых ресурсов в облаке, прогон на настоящей модели в объёме больше пробы.
- **Веди журнал.** Пользователь поправил твоё утверждение, ревью нашло дефект, запуск опроверг написанное — допиши строку в конец таблицы в `docs/development/JOURNAL.md` сразу. Честно: кто поймал и как.

## 4. Проверить перед PR

1. `make test` и линтер, если они уже есть в репозитории. Красное — PR не открывается.
2. Просмотри собственный дифф целиком: `git diff origin/main`. Ищи секреты, адреса, идентификаторы проектов, личные данные, отладочные остатки. Репозиторий публичный.
3. Убедись, что в коде сервиса нет ничего из содержимого `data/`: идентификаторов документов, пользователей, оборудования, чисел.
4. Сверь сделанное с критериями приёмки по одному. Не сделано — так и запиши, не подгоняй формулировку.

## 5. Открыть PR

Коммит, пуш и PR делаются, когда пользователь попросил довести задачу до PR; запуск этого скилла по номеру задачи такой просьбой считается.

Описание PR — по шаблону. Раздел «Что не сделано» обязателен: пустым он бывает редко, и по нему проверяющий судит о честности остального.

```
## Что сделано

- …

## Как проверено

- что запускалось и с каким результатом; что проверено только чтением

## Что не сделано

- …

Closes #<номер>
```

`Closes` — только если выполнены все критерии. Если задача сделана частично, пиши `Refs #<номер>` и перечисли оставшееся.

После создания PR отметь в теле задачи выполненные критерии — только те, что действительно выполнены и проверены.

## 6. Ревью

Запусти скилл `independent-review` по этому PR. Находки исправляются новыми коммитами в той же ветке, без переписывания истории. Если после ревью меняется что-то, что проверялось запуском, запусти снова.

Слияние делает человек. Не сливай PR и не одобряй его, пока пользователь прямо не сказал слить этот PR. Способ — squash, один коммит на задачу.

## 7. После слияния

```
git worktree remove ../oes-agent-assistant.worktrees/<тип>/<номер>-<кратко>
git branch -D <тип>/<номер>-<кратко>
git pull --ff-only origin main
```

Перед удалением рабочей копии посмотри, не осталось ли в ней того, что не попало в git и ещё нужно: файла состояния Terraform, результатов прогона.

## Если PR зависит от другого открытого PR

Скажи об этом в описании и назови порядок слияния. Два PR, правящие один и тот же файл в одном месте, дадут конфликт: `JOURNAL.md` и `CLAUDE.md` меняются чаще всего, записи в журнал добавляй в конец таблицы.
