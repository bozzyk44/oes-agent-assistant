# Ассистент сотрудника с правами доступа

Тестовое задание на позицию Tech Lead (корпоративные ИИ-агенты). Сервис для вымышленного рудника АО «Северная руда»: агент на LLM отвечает сотрудникам по регламентам и показателям и готовит заявку на ремонт оборудования. Задание — в [docs/business/TASK.md](docs/business/TASK.md).

Сервис соблюдает четыре правила:

1. **Права.** Агент видит только то, что видит пользователь; проверяет код, а не промпт.
2. **Бюджет.** Лимит вызовов модели и токенов соблюдается при сборке входа.
3. **Запись.** Заявка создаётся только после подтверждения и ровно один раз.
4. **Измеримость.** Качество, утечки и стоимость измеряются прогоном по эталонным вопросам.

## Запуск

Нужны только Docker и make. Проверено на Docker Engine 29 и Compose 5. Файл compose использует `start_interval`, поэтому Engine должен быть версии 25 или новее.

```sh
make test      # линтер, типы и тесты — без сети и без модели
make data      # набор в data/ — уже лежит в репозитории, команда его воспроизводит
make env       # .env со случайными секретами; затем впишите в него модель и цены — раздел «Модель»
make run       # PostgreSQL, миграции, загрузка набора, сервис и заглушка ТОиР; работает в переднем плане
make eval      # из второго терминала: прогон эталонных вопросов — с настоящей моделью, платно
```

Модель сервис читает при старте. Если вписать её в `.env` после `make run`, остановите запуск и выполните `make run` снова. Без модели сервис стартует, но каждый ход отвечает `outcome: error` с причиной. Цены `PRICE_*` нужны только отчёту прогона. Сервис доступен на `http://127.0.0.1:8000`. Пример хода и подтверждения заявки на наборе из репозитория; `action_id` — из поля `pending_action` ответа, если модель предложила заявку:

```sh
curl -s 127.0.0.1:8000/turn -H 'X-User-ID: u-makarov' -H 'Content-Type: application/json' \
  -d '{"session_id": "demo-1", "message": "Оформи заявку на ремонт экскаватора EX-02: течь в гидросистеме напора"}'
curl -s -X POST 127.0.0.1:8000/actions/<action_id из pending_action>/confirm -H 'X-User-ID: u-makarov'
```

| Команда | Что делает |
|---|---|
| `make run` | Создаёт `.env`, если его нет, и поднимает PostgreSQL, шаги ролей, миграций и загрузки набора, сервис и заглушку ТОиР |
| `make down` | Останавливает запуск; том базы остаётся |
| `make reset` | Останавливает запуск и удаляет том базы. Нужна, если `.env` создан заново: пароль администратора PostgreSQL запоминается в томе |
| `make test` | Линтер, типы и тесты, без сети и без модели. PostgreSQL поднимается в контейнере, модель заменена заглушкой со сценарием |
| `make data` | Пишет набор в `data/`: пользователей, три таблицы КХД, документы и эталонные вопросы. Проверяет формат и состав, в том числе что строки `forbidden` не встречаются в данных автора вопроса. Зерно постоянное |
| `make data-holdout` | Тот же генератор с другим зерном в `holdout/`: набор, на котором промпт не настраивался |
| `make eval QUESTIONS=<путь>` | Каждый вопрос `EVAL_ATTEMPTS` раз (по умолчанию 3) в своих сессиях. Пишет `eval/results.jsonl` и `eval/report.md`. По умолчанию вопросы — `$DATA_DIR/questions.jsonl` |
| `make eval-report` | Пересобирает `eval/report.md` из `eval/results.jsonl` без сервиса |
| `make eval-compare A=… B=…` | Сравнивает два прогона из `eval/runs/` попарно по вопросам; конфигурации должны отличаться ровно в одном поле |
| `make mutants` | Прогон против сборок сервиса с одной отключённой защитой; таблица — `eval/mutants/mutants.md`. По умолчанию со сценарной заглушкой; `MUTANT_MODE=model` — с настоящей моделью, платно |
| `make migrate` | Применяет миграции к базе текущего запуска; `make run` делает это сам |
| `make ci` | Проверка миграций, `make test` и сценарий сборки на чистой копии текущего коммита |

**Свой набор данных** — переменная `DATA_DIR`. При смене набора загрузчик перезагружает данные по хэшу и очищает сессии. **Второй клон репозитория** делит с первым контейнеры и том базы. Чтобы развести их, задайте `COMPOSE_PROJECT=<имя>`.

## Модель

Модель задаётся тремя переменными в `.env` или в окружении оболочки: `MODEL_BASE_URL`, `MODEL_API_KEY`, `MODEL_NAME`. Адрес и имя обязательны, а ключ можно оставить пустым, если серверу модели он не нужен. Цены для отчёта — `PRICE_INPUT`, `PRICE_CACHED`, `PRICE_OUTPUT`, в долларах за 1 млн токенов.

Пример для модели на той же машине через Ollama:

```sh
MODEL_BASE_URL=http://host.docker.internal:11434/v1
MODEL_API_KEY=
MODEL_NAME=qwen3:32b
```

- **`host.docker.internal`, а не `localhost`.** Внутри контейнера `localhost` — это сам контейнер. На Linux без Docker Desktop это имя ведёт на адрес моста Docker, поэтому модель должна слушать не только локальный адрес. Для Ollama — `OLLAMA_HOST=0.0.0.0`.
- **Окно контекста.** У локальных серверов оно по умолчанию мало для этого сервиса: вход одного вызова доходит до 8 000 токенов плюс выход. У Ollama задайте контекст не меньше 10 240 токенов: переменной `OLLAMA_CONTEXT_LENGTH` сервера или `num_ctx` в Modelfile; параметр запроса через OpenAI-совместимый адрес для этого не годится. У vLLM — `--max-model-len`. Иначе Ollama молча обрежет вход, а vLLM отклонит запрос.

Необязательные настройки описаны в `.env.example`:

- `MODEL_MAX_OUTPUT_TOKENS` и `MODEL_TIMEOUT_SECONDS`;
- `MODEL_RESPONSE_FORMAT` — `last`, `all` или `off`;
- `MODEL_EXTRA_BODY` — JSON, добавляется к телу запроса, например чтобы выключить рассуждения модели. У модели с рассуждениями без этого рассуждения тратят потолок выхода, а ответ, оборванный по длине, итогом не считается;
- `MODEL_TOKEN_CHARS` — символов на токен для оценки входа.

## Что сделано

- **Генератор набора:**
  - пользователи, таблицы КХД, документы;
  - 18 эталонных вопросов с ловушками прав, записи, редакций и инструкции в документе;
  - формулировки вопросов, разметка фрагментов, атаки для мутантов.
- **Сервис:** `POST /turn`, `POST /actions/{id}/confirm`, `POST /actions/{id}/reject`, плюс запись хода `GET /turns/{id}` и сведения о сборке `GET /info`. Агентный цикл свой, поверх `openai` SDK, с пятью инструментами — решение 2.
- **Права** держат два барьера. Первый — слой доступа в коде до попадания данных во вход модели. Второй — построчная защита PostgreSQL. Каждый барьер по отдельности не даёт утечек, это показали мутанты.
- **Запись:** автомат действия в базе, ключ идемпотентности, заявка ровно одна при повторе, гонке и рестарте.
- **Бюджет:** проверка до отправки по локальной оценке токенов с поправкой по фактическому расходу; потолок результата инструмента; стабильный `prefix_hash`.
- **Заглушка ТОиР** — отдельный процесс со своей базой и ролью.
- **Прогон:** попытки, проверки контракта, диагностика по записи хода, сравнение прогонов, проигрывание записанных ходов в CI без модели.
- **Мутанты**: шесть сборок с одной отключённой защитой и две с одним барьером прав.
- **Локальный CI** на чистой копии коммита и GitHub Actions второй машиной.
- **Сервер стенда** описан в Terraform для Cloud.ru, создание и удаление проверены — [STAND.md](docs/development/STAND.md).

## Работа с ИИ

**Инструменты.** Claude Code: основной агент пишет код, тесты, документы и данные. Ревью делают отдельные агенты на Sonnet с чистым контекстом — кругами, пока не останется существенных находок. Ещё одно ревью — встроенное ревью диффа `/code-review`. Порядок работы записан в [CLAUDE.md](CLAUDE.md) и скиллах [.claude/skills/](.claude/skills/): задача с критериями приёмки → ветка → черновик PR → локальный CI → ревью агентом → ревью человека → слияние.

**Что сгенерировано.** Почти весь код, тесты, генератор набора и черновики документов. Решения и отвергнутые варианты сначала записаны в документы, потом по ним написан код.

**Где правил человек.** Архитектурные решения: данные и полномочия — в базе с построчной защитой, а не в памяти процесса; одна база вместо SQLite для заглушки; наблюдаемость одним контейнером вместо стека на половину памяти сервера. Порядок ревью: кругами, а не одним проходом. В обсуждении PR #51 — правило в промпте: модель не называет заявку подготовленной, пока нет черновика.

**Пойманные ошибки ИИ** — три из журнала [JOURNAL.md](docs/development/JOURNAL.md), где записан каждый случай:

1. **Человек поймал архитектурное упрощение.** Агент предложил держать набор и пользователей в памяти процесса, «для простоты и срока». Человек: схема не похожа на продуктовую и не использует базу там, где она даёт гарантию. Данные и полномочия переехали в PostgreSQL, и у прав появился второй барьер — построчная защита. Мутанты потом показали, что каждый барьер по отдельности держит утечки. Запись 2, решение 6.
2. **Ревью агентом поймало дыру, внесённую правкой по ревью.** Во втором круге агент исправил находку: идентификатор оборудования стал сравниваться по ключу без регистра и дефисов. Функция при этом брала первую строку с совпавшим ключом. На наборе, где `EX-1` стоит на своём участке, а `EX1` — на чужом, заявка на чужое оборудование проходила проверку прав, а второго барьера у этой проверки нет. Третий круг ревью новым агентом это нашёл. Теперь точное совпадение важнее ключа, а неоднозначный ключ не находит ничего. Запись 65. Отсюда правило: правку по ревью проверяет новый агент.
3. **Тест поймал то, что агент повторял.** В комментариях к коду агент по памяти писал идентификаторы оборудования из `data/`, нарушая правило «код не знает набора». Первый раз он заметил это сам и написал тест, который ищет идентификаторы обоих наборов генератора в исходниках сервиса. Ещё три таких случая за день ловил уже тест, до коммита. Записи 61 и 71. Вывод: правило, которое агент знает, всё равно держится проверкой, а не вниманием.
