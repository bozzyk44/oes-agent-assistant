# Стенд в облаке

Как создать и удалить сервер стенда. Что это за сервер и почему он такой — в [INFRASTRUCTURE.md](../architecture/INFRASTRUCTURE.md) и решении 9 в [DECISIONS.md](../architecture/DECISIONS.md).

Стенд — дополнение к локальному запуску. Для проверки задания он не нужен.

## Что нужно

- Docker. Terraform ставить не надо: он запускается в контейнере.
- Ключ сервисного аккаунта Cloud.ru с правом управлять виртуальными машинами и идентификатор проекта.
- Публичный SSH-ключ.

| Переменная | Что это | По умолчанию |
|---|---|---|
| `CLOUD_RU_KEY_ID`, `CLOUD_RU_KEY_SECRET` | Ключ сервисного аккаунта | нет, обязательны |
| `CLOUD_RU_PROJECT_ID` | Идентификатор проекта | нет, обязательна |
| `STAND_SSH_PUBLIC_KEY_FILE` | Путь к публичному SSH-ключу | `~/.ssh/id_ed25519.pub` |
| `ENV_FILE` | Откуда читать переменные выше | `.env` в корне репозитория |
| `TERRAFORM_VERSION` | Версия образа Terraform | `1.9.8` |

Скрипт берёт четыре первые переменные из окружения, а если их там нет — из файла окружения. Файл не исполняется, из него читаются только эти строки. В рабочей копии ветки `.env` — ссылка на файл основного каталога; её создаёт скрипт скилла `take-issue`.

## Команды

Из корня репозитория:

| Команда | Что делает |
|---|---|
| `infra/terraform/tf.sh init` | Скачивает провайдер. Нужна один раз |
| `infra/terraform/tf.sh plan` | Показывает, что будет создано |
| `infra/terraform/tf.sh apply` | Создаёт стенд; спрашивает подтверждение |
| `infra/terraform/tf.sh output` | Адрес сервера, команда входа, адрес сервиса |
| `infra/terraform/tf.sh destroy` | Удаляет всё созданное; спрашивает подтверждение |

Создание занимает около четырёх минут, удаление — около двух. После `apply` сервер ещё две-три минуты настраивает себя сам. Готовность проверяется на сервере командой `cloud-init status --wait`: `status: done` — готов, `status: error` — настройка не удалась, и `apply` об этом не узнает.

Переменные Terraform задаются окружением с приставкой `TF_VAR_` и должны быть одинаковыми при каждой команде:

```
TF_VAR_ssh_cidr=203.0.113.7/32 infra/terraform/tf.sh apply
```

## Что создаётся

| Ресурс | Параметры |
|---|---|
| Группа безопасности | Входящие: SSH; порт сервиса — только если задан `service_cidr`. Исходящие: любые |
| Загрузочный диск | SSD, 30 ГБ, Ubuntu 24.04 |
| Сетевой интерфейс | В подсети проекта по умолчанию |
| Публичный IP | Один |
| Сервер | 2 vCPU с долей 10 %, 4 ГБ |

При первом запуске сервер ставит Docker, Compose, make и git, создаёт файл подкачки на 1 ГБ и пользователя с входом по ключу. Развёртывание самого сервиса сюда пока не входит: оно добавится, когда появится compose.

## Миграции при деплое

Развёртывание сервиса на стенд — это `docker compose up` на сервере, и миграции в нём — отдельный шаг, а не часть загрузки данных: сервис `migrate` стартует после шага ролей и баз и до загрузчика набора. Решение 11 в [DECISIONS.md](../architecture/DECISIONS.md).

| Что | Как |
|---|---|
| Когда выполняется | При каждом `docker compose up` на сервере, перед загрузкой набора и стартом сервиса. Отдельно, без перезапуска остального: `make migrate` |
| Что делает на актуальной базе | Ничего: сообщает «схема уже на последней версии» |
| Что происходит при ошибке | Шаг завершается с ненулевым кодом; загрузчик набора и сервис после него не стартуют. Причина — в `docker compose logs migrate`. Что при этом происходит с уже работающим контейнером сервиса прежней версии, не проверено |
| Как проверить версию схемы | `docker compose logs migrate`: последняя строка называет версию. Загрузчик набора сверяет её сам и на отставшей схеме останавливается |
| Проверено ли заранее | Те же миграции в CI применяются на пустую базу, повторно, откатываются и применяются снова: `make migrate-check` |
| Откат | На стенде — удалить том базы (`make reset`) и поднять заново: невосстановимого на сервере нет. Автоматического отката схемы при деплое нет |

Самого развёртывания сервиса на стенде ещё нет: этот раздел описывает шаг, который в него войдёт, и на живом стенде не проверен.

## Доступ и безопасность

1. **Порт сервиса по умолчанию закрыт.** У сервиса нет аутентификации: по условию задания заголовок `X-User-ID` считается доверенным. Открытый порт — это возможность для любого читать данные набора от имени любого пользователя, подтверждать заявки и тратить деньги на ключе модели. Порт открывается переменной `service_cidr` для конкретного адреса или сети.
2. **Открывать порт всем можно только осознанно** и только при выставленном лимите расхода на ключе ИИ-роутера: это единственное, что тогда ограничивает ущерб.
3. **SSH открыт отовсюду, вход только по ключу.** Вход по паролю и под root выключен. Сузить можно переменной `ssh_cidr`.
4. **Пользователь сервера — администратор:** у него `sudo` без пароля и доступ к Docker. Для стенда с одним ключом это приемлемо.
5. **Группа безопасности — единственный внешний барьер.** Docker публикует порты контейнеров в обход экрана на самом сервере, поэтому PostgreSQL, заглушка ТОиР и наблюдаемость в compose не должны публиковать порты наружу.
6. **На сервер не копируется локальный `.env` целиком.** В нём лежит ключ сервисного аккаунта облака, а серверу он не нужен. Сервису нужны только переменные модели, базы и ТОиР.

## Что проверено

На живом облаке, 2026-10-13, три полных цикла создания и удаления:

| Проверка | Результат |
|---|---|
| Создание и удаление всех ресурсов | Да; после удаления через API подтверждено, что серверов, дисков и публичных адресов в проекте нет |
| Вход по SSH под созданным пользователем | Да |
| Вход под root и по паролю | Закрыт |
| Docker, Compose, подкачка после первой настройки | Да; настройка заняла около трёх минут |
| Запуск контейнера на сервере и доступ с сервера к ИИ-роутеру | Да |
| Порт сервиса при незаданном `service_cidr` | Снаружи не отвечает |
| Порт сервиса при заданном `service_cidr`, порт PostgreSQL | Первый отвечает, второй нет |
| Скрипт под штатным bash macOS версии 3.2 и без терминала | Работает |

## Особенности провайдера

То, на чём спотыкались версии конфигурации.

1. **Провайдера нет в общем реестре Terraform.** Он ставится с зеркала Cloud.ru; адрес — в `infra/terraform/terraform.rc`, скрипт подключает его сам. Подлинность провайдера удостоверяет только контрольная сумма в `.terraform.lock.hcl`: этот файл нельзя удалять и пересоздавать не глядя.
2. **Нет сборки провайдера под linux/arm64.** Контейнер с Terraform всегда запускается как amd64; на машинах с ARM — через эмуляцию, поэтому команды идут заметно медленнее.
3. **Порт в правиле группы безопасности задаётся диапазоном**, даже если он один: `22:22`. С одиночным значением правило создаётся, но `apply` завершается ошибкой о несогласованном результате.
4. **Серверу нельзя передать одновременно метаданные образа и cloud-init.** Пользователь, ключ и имя хоста заданы в cloud-init.
5. **Каждая операция с ресурсом занимает около тридцати секунд**, даже удаление правила.
6. **Установка пакетов при первом запуске конкурирует с фоновым обновлением системы.** Штатный модуль cloud-init ждёт блокировку менеджера пакетов тридцать секунд и сдаётся: во втором цикле проверки сервер из-за этого поднялся без Docker. Пакеты ставятся командой с ожиданием блокировки и повторами.
7. **Изменение правил группы безопасности на работающем сервере действует не сразу.** В проверке после удаления правила порт отвечал снаружи ещё не меньше минуты. Закрывать порт сменой переменной на работающем стенде ненадёжно: нужное значение `service_cidr` задаётся при создании, а для срочного закрытия стенд удаляется.

## Что не пересоздаёт сервер

Смена SSH-ключа, имени пользователя и обновление образа провайдером сервер и диск не пересоздают: первая настройка выполняется один раз. Чтобы применить такие изменения, стенд удаляется и создаётся заново.

## Состояние Terraform

Файл состояния лежит локально в `infra/terraform/` и в репозиторий не попадает. В нём нет ключа сервисного аккаунта, но есть идентификатор проекта, адрес сервера и публичный SSH-ключ. Для стенда, который создаёт один человек, локального файла достаточно. Удалять стенд нужно с той же машины, где он создан, либо перенести файл состояния.
