# Стенд в облаке

Как создать и удалить сервер стенда. Что это за сервер и почему он такой — в [INFRASTRUCTURE.md](../architecture/INFRASTRUCTURE.md) и решении 9 в [DECISIONS.md](../architecture/DECISIONS.md).

Стенд — дополнение к локальному запуску. Для проверки задания он не нужен.

## Что нужно

- Docker. Terraform ставить не надо: он запускается в контейнере.
- Ключ сервисного аккаунта Cloud.ru с правом управлять виртуальными машинами и идентификатор проекта.
- Публичный SSH-ключ.

| Переменная | Что это | По умолчанию |
|---|---|---|
| `CLOUD_RU_KEY_ID`, `CLOUD_RU_KEY_SECRET` | Ключ сервисного аккаунта | нет, обязательны |
| `CLOUD_RU_PROJECT_ID` | Идентификатор проекта | нет, обязательна |
| `STAND_SSH_PUBLIC_KEY_FILE` | Путь к публичному SSH-ключу | `~/.ssh/id_ed25519.pub` |
| `ENV_FILE` | Откуда читать переменные выше | `.env` в корне репозитория |
| `TERRAFORM_VERSION` | Версия образа Terraform | `1.9.8` |

Скрипт берёт четыре первые переменные из окружения, а если их там нет — из файла окружения. Файл не исполняется, из него читаются только эти строки. В рабочей копии ветки `.env` — ссылка на файл основного каталога; её создаёт скрипт скилла `take-issue`.

## Одной командой

| Команда | Что делает |
|---|---|
| `make stand` | Создаёт сервер (`apply` спрашивает подтверждение — это платное действие), ждёт первой настройки и разворачивает сервис |
| `make stand-deploy` | Выкатывает текущий коммит на уже созданный сервер |
| `make stand-destroy` | Удаляет стенд; спрашивает подтверждение |

Переменные Terraform (`TF_VAR_service_cidr` и другие) задаются так же, как для `tf.sh`, — окружением при `make stand`.

### Сервер из панели, например бесплатный

У Cloud.ru есть бесплатный сервер в той же конфигурации — 2 vCPU с долей 10 %, 4 ГБ, диск 30 ГБ; платится только публичный адрес. Terraform его не создаёт: у провайдера нет такого признака, он заказывается в панели. Сервис на него разворачивается тем же сценарием:

1. В форме создания: Ubuntu 24.04, новый публичный адрес, свой логин не короче пяти символов — `oes` форма не принимает; проверялся `oemadmin`, метод — публичный ключ из `STAND_SSH_PUBLIC_KEY_FILE`. Cloud-init стенда (`make stand-cloud-init`) форма 2026-10-15 отклонила без объяснения причин — особенность 10 ниже; без него Docker и подкачку ставит сама выкатка.
2. Когда сервер создан: `STAND_LOGIN=<логин> STAND_HOST=<логин>@<адрес> make stand-deploy`. Сценарий ждёт окончания первой настройки, ставит Docker, если его нет, и разворачивает сервис так же, как на сервере из Terraform.

Группа безопасности у такого сервера — та, что выбрана в панели; порт сервиса в ней открывать не нужно, проверка — через SSH-туннель. Удаляется такой сервер в панели: `make stand-destroy` его не знает.

## Команды Terraform

Из корня репозитория:

| Команда | Что делает |
|---|---|
| `infra/terraform/tf.sh init` | Скачивает провайдер. Нужна один раз |
| `infra/terraform/tf.sh plan` | Показывает, что будет создано |
| `infra/terraform/tf.sh apply` | Создаёт стенд; спрашивает подтверждение |
| `infra/terraform/tf.sh output` | Адрес сервера, команда входа, адрес сервиса |
| `infra/terraform/tf.sh destroy` | Удаляет всё созданное; спрашивает подтверждение |

Создание занимает около четырёх минут, удаление — около двух. После `apply` сервер ещё две-три минуты настраивает себя сам. Готовность проверяется на сервере командой `cloud-init status --wait`: `status: done` — готов, `status: error` — настройка не удалась, и `apply` об этом не узнает.

Переменные Terraform задаются окружением с приставкой `TF_VAR_` и должны быть одинаковыми при каждой команде:

```
TF_VAR_ssh_cidr=203.0.113.7/32 infra/terraform/tf.sh apply
```

## Что создаётся

| Ресурс | Параметры |
|---|---|
| Группа безопасности | Входящие: SSH; порт сервиса — только если задан `service_cidr`. Исходящие: любые |
| Загрузочный диск | SSD, 30 ГБ, Ubuntu 24.04 |
| Сетевой интерфейс | В подсети проекта по умолчанию |
| Публичный IP | Один |
| Сервер | 2 vCPU с долей 10 %, 4 ГБ |

При первом запуске сервер ставит Docker, Compose, make и git, создаёт файл подкачки на 1 ГБ и пользователя с входом по ключу.

## Развёртывание сервиса

`scripts/stand.sh` — сценарий на машине разработчика, `scripts/stand-remote.sh` — его часть, которая выполняется на сервере.

| Шаг | Как |
|---|---|
| Ожидание сервера | SSH отвечает, затем `cloud-init status --wait`: Docker поставлен. Ключ хоста — в `.stand/known_hosts`, не в общем файле: при пересоздании стенда адрес может повториться с новым ключом |
| Код | Закоммиченный `HEAD` через `git archive` — вместе с `data/`. Незакоммиченное не выкатывается, как и в локальном CI. GitHub не нужен |
| `.env` на сервере | Постоянный файл `~/oes/.env`; в каталоге кода — ссылка на него. При первой выкатке его создаёт `make-env.sh` со своими случайными паролями базы и `TOIR_TOKEN`; при следующих он сохраняется — пароли должны совпадать с томом базы |
| Что уходит с локальной машины | Только настройки модели и цены: `MODEL_*` и `PRICE_*`. Каждое имя передаётся при каждой выкатке, отсутствующее — пустым. Передача — через stdin SSH, не в аргументах. Ключа облака, паролей локальной базы и `TOIR_TOKEN` на сервере нет |
| Порт | `SERVICE_BIND=0.0.0.0`: порт сервиса публикуется на всех адресах сервера, снаружи его закрывает группа безопасности, пока не задан `service_cidr`. Остальные контейнеры портов не публикуют |
| Запуск | `docker compose -p oes-assistant up -d --build --wait` — те же шаги, что у `make run`: роли и базы, миграции, загрузка набора, сервис и заглушка ТОиР. Затем удаляются старые образы, и сценарий проверяет `GET /info` на сервере |

Проверить сервис с машины, адрес которой не открыт в `service_cidr`, можно через туннель: `ssh -L 8000:127.0.0.1:8000 oes@<адрес>`, затем запросы на `http://127.0.0.1:8000`.

## Миграции при деплое

Развёртывание сервиса на стенд — это `docker compose up` на сервере, и миграции в нём — отдельный шаг, а не часть загрузки данных: сервис `migrate` стартует после шага ролей и баз и до загрузчика набора. Решение 11 в [DECISIONS.md](../architecture/DECISIONS.md).

| Что | Как |
|---|---|
| Когда выполняется | При каждом `docker compose up` на сервере, перед загрузкой набора и стартом сервиса. Отдельно: `make migrate` — сервис при этом не перезапускается — это проверяет сценарий сборки; шаг ролей и баз выполняется как зависимость и заново выставляет ролям пароли из окружения |
| Что делает на актуальной базе | Ничего: сообщает «схема уже на последней версии» |
| Что происходит при ошибке | Шаг завершается с ненулевым кодом; загрузчик набора и сервис после него не стартуют. Причина — в `docker compose logs migrate`. Что при этом происходит с уже работающим контейнером сервиса прежней версии, не проверено |
| Как проверить версию схемы | `make migrate` печатает её сам: «схема уже на последней версии: …». После `docker compose up` версия — в `docker compose logs migrate`; вывод отдельного `make migrate` туда не попадает. Загрузчик набора сверяет версию сам и на отставшей схеме останавливается |
| База новее кода | Если на сервер выкатили сборку старше той, что мигрировала базу, шаг миграций и загрузчик останавливаются с сообщением «база новее кода» и ничего не меняют |
| Проверено ли заранее | Те же миграции в CI применяются на пустую базу, повторно, откатываются и применяются снова: `make migrate-check` |
| Откат | На стенде — удалить том базы (`make reset`) и поднять заново: невосстановимого на сервере нет. Автоматического отката схемы при деплое нет |

Развёртывание — `make stand` и `make stand-deploy`, раздел «Развёртывание сервиса».

## Доступ и безопасность

1. **Порт сервиса по умолчанию закрыт.** У сервиса нет аутентификации: по условию задания заголовок `X-User-ID` считается доверенным. Открытый порт — это возможность для любого читать данные набора от имени любого пользователя, подтверждать заявки и тратить деньги на ключе модели. Порт открывается переменной `service_cidr` для конкретного адреса или сети.
2. **Открывать порт всем можно только осознанно** и только при выставленном лимите расхода на ключе ИИ-роутера: это единственное, что тогда ограничивает ущерб.
3. **SSH открыт отовсюду, вход только по ключу.** Вход по паролю и под root выключен. Сузить можно переменной `ssh_cidr`.
4. **Пользователь сервера — администратор:** у него `sudo` без пароля и доступ к Docker. Для стенда с одним ключом это приемлемо.
5. **Группа безопасности — единственный внешний барьер.** Docker публикует порты контейнеров в обход экрана на самом сервере, поэтому PostgreSQL, заглушка ТОиР и наблюдаемость в compose не должны публиковать порты наружу.
6. **На сервер не копируется локальный `.env` целиком.** В нём лежит ключ сервисного аккаунта облака, а серверу он не нужен. Сервису нужны только переменные модели, базы и ТОиР.

## Что проверено

Развёртывание сервиса — на живом сервере из панели, 2026-10-15: `ru.AZ-2`, конфигурация `lowcost10-2-4`, Ubuntu 24.04, без cloud-init стенда.

| Проверка | Результат |
|---|---|
| Подготовка сервера без cloud-init стенда | Выкатка поставила Docker, Compose и подкачку сама. Первая настройка образа панели заканчивается с кодом 2, «degraded done»: это не провал, сценарий его пропускает |
| Сборка на сервере и запуск | Роли и базы, миграции, загрузка набора, сервис и заглушка ТОиР здоровы; `GET /info` — тот же `prefix_hash`, что локально |
| Настоящий ход через SSH-туннель | Ответ с цитатой, 2 вызова модели, 4,2 с |
| Порты | На сервере слушают только SSH и порт сервиса; PostgreSQL и заглушка ТОиР не опубликованы. Снаружи порт сервиса не отвечает: группа безопасности пускает только SSH |
| Память | Сервис около 100 МБ, заглушка около 60 МБ, PostgreSQL около 60 МБ при лимитах 768, 192 и 768 МБ; занято около 0,8 ГБ из 4 ГБ, подкачка не используется. Наблюдаемости ещё нет |

| Повторная выкатка | Пароли базы и `TOIR_TOKEN` не изменились, том базы тот же, сервис снова здоров |

## Особенности провайдера

То, на чём спотыкались версии конфигурации.

1. **Провайдера нет в общем реестре Terraform.** Он ставится с зеркала Cloud.ru; адрес — в `infra/terraform/terraform.rc`, скрипт подключает его сам. Подлинность провайдера удостоверяет только контрольная сумма в `.terraform.lock.hcl`: этот файл нельзя удалять и пересоздавать не глядя.
2. **Нет сборки провайдера под linux/arm64.** Контейнер с Terraform всегда запускается как amd64; на машинах с ARM — через эмуляцию, поэтому команды идут заметно медленнее.
3. **Порт в правиле группы безопасности задаётся диапазоном**, даже если он один: `22:22`. С одиночным значением правило создаётся, но `apply` завершается ошибкой о несогласованном результате.
4. **Серверу нельзя передать одновременно метаданные образа и cloud-init.** Пользователь, ключ и имя хоста заданы в cloud-init.
5. **Каждая операция с ресурсом занимает около тридцати секунд**, даже удаление правила.
6. **Установка пакетов при первом запуске конкурирует с фоновым обновлением системы.** Штатный модуль cloud-init ждёт блокировку менеджера пакетов тридцать секунд и сдаётся: во втором цикле проверки сервер из-за этого поднялся без Docker. Пакеты ставятся командой с ожиданием блокировки и повторами.
7. **Изменение правил группы безопасности на работающем сервере действует не сразу.** В проверке после удаления правила порт отвечал снаружи ещё не меньше минуты. Закрывать порт сменой переменной на работающем стенде ненадёжно: нужное значение `service_cidr` задаётся при создании, а для срочного закрытия стенд удаляется.
8. **Нехватка мощностей выглядит как сбой.** 2026-10-15 сервер `lowcost10-2-4` в `ru.AZ-1` не создался ни через Terraform — три попытки, ошибка `Failed to execute task on the virtualization layer` после десяти минут ожидания, — ни бесплатный из панели: статус `VM_STATUS_ERROR_CREATING`. API при этом показывает конфигурацию доступной во всех зонах. Документация провайдера на такой случай советует подождать, сменить зону или конфигурацию. Подсеть по умолчанию в проекте есть только в `ru.AZ-1`: в другой зоне Terraform остановится на проверке ещё до создания ресурсов.
9. **Неудачное создание сервера оставляет ресурсы.** После отказа облако может удалить сетевой интерфейс вместе с сервером, и повторный `apply` падает на «Interface is not found»; выход — `make stand-destroy` и создание заново. Сервер из панели после отказа остаётся со своим диском и публичным адресом в статусе ошибки, и их нужно удалить вручную.
10. **Форма панели строже API.** Логин `oes` она отклоняет как не соответствующий требованиям, а cloud-init стенда отклоняет целиком с сообщением «Одно или несколько полей заполнены неверно», без указания поля. Для сервера из панели — свой логин (`STAND_LOGIN`) без cloud-init: Docker и подкачку выкатка ставит сама по SSH, `scripts/stand-bootstrap.sh`.

## Что не пересоздаёт сервер

Смена SSH-ключа, имени пользователя и обновление образа провайдером сервер и диск не пересоздают: первая настройка выполняется один раз. Чтобы применить такие изменения, стенд удаляется и создаётся заново.

## Состояние Terraform

Файл состояния лежит локально в `infra/terraform/` и в репозиторий не попадает. В нём нет ключа сервисного аккаунта, но есть идентификатор проекта, адрес сервера и публичный SSH-ключ. Для стенда, который создаёт один человек, локального файла достаточно. Удалять стенд нужно с той же машины, где он создан, либо перенести файл состояния.
