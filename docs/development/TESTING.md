# Стратегия тестирования детерминированной части

Как проверяется всё, что в сервисе не является моделью: права, запись, бюджет хода, загрузка набора, API. Что именно гарантируется — в [ARCHITECTURE.md](../architecture/ARCHITECTURE.md); этот документ отвечает на вопрос, чем каждая гарантия доказана.

Качество ответов модели здесь не проверяется: это задача прогона эталонных вопросов (`make eval`) и отдельного документа. Граница такая: тесты доказывают, что код не даст модели ошибиться опасно; прогон измеряет, как часто она ошибается безопасно.

## Принципы

1. **Проверяется вход модели, а не её ответ.** Утечка — это то, что модель увидела, а не то, что она пересказала. Заглушка модели записывает каждый отправленный ей вход целиком, и тесты прав ищут запрещённое в этих записях.
2. **Без сети и без модели.** Модель заменяет заглушка со сценарием. ТОиР — настоящее приложение заглушки, поднятое в том же процессе тестов, а не подмена функции: проверяется и клиент, и приёмник.
3. **На настоящем PostgreSQL.** Полнотекстовый поиск, построчная защита и условные обновления есть только в нём. `make test` поднимает базу в локальном контейнере; тот же образ, что в запуске.
4. **Таблицы архитектуры — это список тестов.** У каждой строки таблиц «Статусы инструментов», «Подтверждение», «API» и «Бюджет» есть тест с тем же названием. Строка без теста — недоделка, тест без строки — недокументированное поведение.
5. **Тесты не знают содержимого `data/`.** Они работают на маленьком наборе, собранном в самих тестах, и отдельно — как инварианты на любом наборе (раздел «Инварианты на наборе»).
6. **Никаких ожиданий по времени.** Часы и генератор идентификаторов подставляются; срок отметки занятости сессии истекает переводом часов, а не паузой.

## Уровни

| Уровень | Что запускается | Что проверяет | Доля тестов |
|---|---|---|---|
| Модульные | Чистые функции, без базы и HTTP | Логику с перебором случаев | Большинство |
| С базой | Код доступа и загрузчик на PostgreSQL | Запросы, политики, поиск, загрузку | Заметная |
| Сервис целиком | API в процессе тестов, заглушка модели, заглушка ТОиР, PostgreSQL | Гарантии задания от запроса до ответа | Немного, но все обязательные |
| Сборка | `docker compose up` и один сценарий снаружи | Что всё стартует и связано | Один-два |

### Модульные

| Что | Случаи |
|---|---|
| Оценка токенов | Оценка не меньше фактического расхода на записанных образцах; поправка коэффициента идёт только вверх; учитываются схемы инструментов и накладные на сообщение |
| Проверка бюджета | Каждая из трёх границ по отдельности: на границе проходит, на единицу больше — нет |
| Сборка входа | Порядок отбрасывания: сначала старые ходы, потом ранние результаты; неизменная часть не трогается никогда |
| Определение последнего вызова | По номеру и по остатку бюджета |
| Неизменная часть | Один и тот же хэш при любом порядке объявления инструментов и полей; в ней нет времени, идентификаторов и сведений о пользователе |
| Обрезка результата инструмента | Не больше 1 500 токенов по оценке; есть пометка и ссылка на продолжение |
| Разбиение документов | Текст до первого заголовка; раздел длиннее потолка; таблица на границе части; документ без заголовков |
| Таблица статусов и `outcome` | Каждая из восьми строк на обоих путях разбора ответа; порядок применения строк |
| Разбор итога хода | Чистый объект; объект в блоке кода и с текстом вокруг; объект без части полей; повреждённый JSON; простой текст с цитатами в скобках и без них; блок размышлений перед объектом; кавычки и переносы строк внутри `answer` |
| Автомат действия | Полная матрица «статус × событие»: разрешённые переходы проходят, все остальные отклоняются |
| Проверка идентификатора в словах пользователя | Регистр, пробелы, дефисы; идентификатор только в тексте документа — отказ; идентификатор только в прошлом сообщении сессии — отказ; идентификатор как часть другого — отказ; похожие кириллические и латинские буквы — принят |
| Сравнение строк прогона | Регистр, пробелы между цифрами, запятая между цифрами; примеры из задания |
| Проверка формата набора | По одному нарушению на каждое правило; неизвестные поля и значения принимаются |

### С базой

| Что | Случаи |
|---|---|
| Миграции | Применяются на пустую базу; повторное применение ничего не меняет |
| Создание ролей и баз | Идемпотентно; смена пароля в окружении при существующем томе не ломает вход; роль сервиса не может подключиться к базе `toir`, роль заглушки — к базе сервиса |
| Загрузка набора | Тот же хэш — ничего не меняется, сессии и действия целы; другой хэш — данные заменены, сессии очищены; ошибка формата посреди загрузки — прежний набор остался целиком |
| Политики построчной защиты | Запросы под ролью сервиса напрямую, в обход слоя доступа: видны только разрешённые строки; без привязки к пользователю и с пустой привязкой — ни одной; привязка не переживает транзакцию на том же соединении |
| Функции в обход политик | Возвращают одно значение; роль без права вызова получает отказ; признак закрытого лучшего совпадения не срабатывает на запрос из одних чисел и на одно слово и не зависит от того, пуста ли доступная выдача |
| Слой доступа | Каждая строка таблицы «Барьер в коде»; явный запрос чужого участка — `denied`; фильтр по оборудованию чужого участка — `denied`; пустой результат по своему участку — `empty`, а не отказ; смешанный запрос — данные по своему и список отказанных |
| Запросы КХД | Агрегаты и группировки; простой через полночь делится между сутками; простой на границе периода учитывается частью; производные колонки |
| Поиск | Словоформы находят друг друга; «ё» и «е»; идентификатор с дефисом и числом ищется точно; запрос из пяти слов не даёт пустую выдачу; утратившая силу редакция не в выдаче по умолчанию и помечена при явном запросе |
| Захват сессии | Второй захват — отказ; после истечения срока — успех; завершение хода снимает отметку; ход, переживший срок, не записывается поверх нового; ошибка в ходе снимает отметку сразу |

Два барьера прав проверяются отдельно и намеренно по-разному. Тест кода убеждается, что запрос построен верно. Тест политик убеждается, что неверно построенный запрос всё равно ничего не отдаст — поэтому он ходит мимо слоя доступа.

### Сервис целиком

Семь обязательных проверок задания, каждая — отдельный тест с названием из задания.

| № | Проверка | Сценарий заглушки модели | Что утверждается |
|---|---|---|---|
| 1 | Документ без доступа не попадает во вход | Ищет по теме закрытого документа; запрашивает его по идентификатору | Ни одного фрагмента закрытого документа нет ни в одном записанном входе |
| 2 | Строки КХД чужого участка не попадают во вход | Явно запрашивает чужой участок; запрашивает без фильтра | Во входах нет ни одной строки и ни одного агрегата по чужому участку |
| 3 | Заявка | Предлагает заявку | Без подтверждения в заглушке ТОиР ноль заявок; два подтверждения — одна заявка и один `request_id`; чужой пользователь — 403 и ноль заявок; сбой после вызова ТОиР и повтор — одна заявка |
| 4 | Заявка на чужой участок | Предлагает заявку на чужое оборудование | `pending_action` пуст, действия в базе нет, в ТОиР ноль заявок |
| 5 | Лимиты | Бесконечно вызывает инструменты; инструмент возвращает результат больше лимита | Вызовов не больше 4; ни один вход не больше 8 000; сумма не больше 24 000; результат инструмента во входе не больше 1 500 |
| 6 | Секрет | Любой из сценариев выше | Значение `TOIR_TOKEN` не встречается во входах модели, ответах API и журнале вызовов модели |
| 7 | `prefix_hash` | Несколько ходов одной сессии | Хэш одинаков во всех вызовах и ходах и совпадает с хэшем записанной неизменной части |

Сверх обязательных:

| Что | Случаи |
|---|---|
| Коды API | Каждая ячейка таблицы «API», включая 401 без заголовка, 409 при втором ходе в занятой сессии и 404 на чужую запись хода |
| Атомарность хода | Исключение перед завершающей транзакцией: в истории нет сообщений этого хода, действия нет, сессия свободна сразу |
| Один `session_id` у двух пользователей | Две независимые сессии; история первого не попадает во вход второго |
| Инструкция в документе | Заглушка, «послушавшись» документа, вызывает подготовку заявки: действие не создаётся, `outcome` не `action` |
| Модель нарушает запрет инструментов на последнем вызове | Инструмент не выполняется; ход завершается текстом или `budget_exceeded` |
| Неверные аргументы инструмента | Модель получает ошибку разбора как результат; ход не падает |
| Сервер отклонил параметр формата ответа | Запрос повторён без параметра и посчитан в лимит; принуждение выключено для следующих ходов; параметр формата не уходит на вызовах с разрешёнными инструментами при настройке по умолчанию |
| Ошибка модели | `outcome: error`, расход сделанных вызовов сохранён |

### Сбои при записи

Гарантия «ровно один раз» проверяется перебором точек сбоя, а не одним счастливым сценарием. Клиент ТОиР и запись результата подставляются в модуль действий снаружи; тест заменяет их обёртками, которые падают в заданный момент.

| Точка сбоя | Ожидание после повторного подтверждения |
|---|---|
| После записи намерения, до вызова ТОиР | Одна заявка, `done` |
| Запрос ушёл, ответ не получен | Одна заявка, `done` |
| Ответ получен, результат не записан | Одна заявка, тот же `request_id`, `done` |
| ТОиР ответил ошибкой сервера | Статус `confirming`, 502; после восстановления — одна заявка |
| ТОиР отверг запрос | `failed`; повтор не вызывает ТОиР |
| Два подтверждения одновременно | Одна заявка, оба ответа с одним `request_id` |
| Подтверждение и отказ одновременно | Побеждает одно; итог согласован: либо `rejected` и ноль заявок, либо `done` и одна |

Рестарт сервиса моделируется созданием нового экземпляра приложения над той же базой: состояние живёт только в ней, и новый экземпляр ничем не отличается от перезапущенного процесса.

Заглушка ТОиР проверяется отдельно как приёмник: повтор ключа, тот же ключ с другим телом, два одновременных запроса с одним ключом, запрос без токена, сохранность после пересоздания приложения.

### Сборка

Один сценарий после `docker compose up` на чистой копии коммита — `make smoke`. Цель — поймать ошибки связки, а не логики: порядок старта, переменные окружения, монтирование набора.

| Что проверяет | Как |
|---|---|
| Без переменных compose не стартует | Пустое окружение: отказ, в сообщении имя переменной и что делать |
| Набор по умолчанию | `DATA_DIR=data/` из образца окружения разрешается в каталог `data` проекта |
| Порядок старта | Загрузчик завершился с кодом 0 раньше, чем стартовали сервис и заглушка |
| Модель из окружения оболочки | Имя модели, заданное только в оболочке, видно в контейнере сервиса |
| Набор приходит с хоста и только на чтение | Каталог с файлом-меткой подставлен через `DATA_DIR`; файл виден в контейнере, запись отклонена даже для суперпользователя контейнера |
| Монтирования прогона | Вопросы и набор читаются, в каталог результатов можно писать; `make eval QUESTIONS=<путь с пробелами>` видит свой файл |
| Связность | Сервис отвечает; заглушка доступна сервису по имени; имя `host.docker.internal` разрешается. Соединение с моделью на хосте не проверяется |
| Порты | Наружу опубликован только порт сервиса и не на всех адресах; у PostgreSQL и заглушки портов нет. Проверяется по сведениям Docker; с хоста на порт сценарий не ходит |
| Перезапуск | Сервис поднимается после перезапуска контейнера; всё поднимается повторно поверх существующего тома базы |

Ход с заглушкой модели, подтверждение заявки и перезапуск сервиса между предложением и подтверждением добавляются в этот же сценарий вместе с ходом и записью: до них сценарию нечего вызывать. Заглушка модели там — тот же сценарный объект, поднятый отдельным контейнером с OpenAI-совместимым адресом.

## Заглушка модели

Заглушка реализует тот же интерфейс, что и клиент модели, и делает две вещи: отдаёт заданную последовательность ответов и вызовов инструментов и записывает каждый полученный вход.

Сценарии делятся на послушные и враждебные. Враждебные важнее: настоящая модель рано или поздно сделает каждое из этих действий.

| Враждебный сценарий | Какую гарантию проверяет |
|---|---|
| Запросить закрытый документ по идентификатору | Права |
| Запросить чужой участок явным фильтром | Права |
| Вызывать инструменты без конца | Бюджет |
| Запросить инструмент после запрета | Бюджет |
| Предложить заявку на чужое оборудование | Запись |
| Предложить заявку на оборудование из текста документа | Данные — не инструкции |
| Передать аргументы не по схеме | Устойчивость |
| Назвать в цитатах фрагмент, которого не было во входе | Цитаты |
| Объявить `refusal` без отказа инструмента и `no_data` при отказе | `outcome` |

## Инварианты на наборе

Отдельная группа тестов не знает, что лежит в наборе, и перебирает его целиком. Она запускается на `data/` и на втором наборе, сгенерированном с другим зерном.

Оба набора даёт фикстура `dataset` в `tests/conftest.py`: тест с ней идёт дважды, на наборе с зерном `data/` и на наборе со вторым зерном, и получает каталог с файлами и параметры генератора. Наборы создаются генератором на время запуска; каталог `data/` из репозитория подключён к тестам только на чтение, и отдельный тест сверяет его с выходом генератора побайтно — правка набора руками не пройдёт.

1. Для каждого пользователя и каждого недоступного ему документа: запрос по идентификатору даёт `denied`, поиск по названию документа не возвращает его фрагментов.
2. Для каждого пользователя, каждой таблицы и каждого участка вне полномочий: запрос возвращает `denied` или не содержит строк этого участка.
3. Для каждого пользователя и каждой единицы оборудования вне его права на заявки: черновик не создаётся.
4. Для каждого пользователя сумма по таблице без фильтра равна сумме по его участкам, посчитанной тестом напрямую из CSV.

Вторая цель этой группы — правило «код не зависит от содержимого набора». Его проверяют два теста: весь набор тестов проходит на наборе с другим зерном, и в исходном коде сервиса нет ни одного идентификатора документа, пользователя или оборудования из `data/`.

## Секреты

На время тестов `TOIR_TOKEN`, ключ модели и пароли базы получают значения-метки, которые не могут встретиться случайно. После каждого теста уровня «сервис целиком» общая проверка ищет метки во всех записанных входах модели, во всех ответах API и в перехваченном журнале. Проверка общая, а не отдельный тест, чтобы новый сценарий получал её без усилий автора.

## Как запускается

| Команда | Что делает |
|---|---|
| `make test` | Линтер, проверка типов, все уровни кроме сборки. Поднимает PostgreSQL в контейнере сама; сеть контейнера тестов внутренняя, выхода наружу нет |
| `make smoke` | Сценарий сборки: поднимает всё с нуля под своим набором-меткой в собственном проекте compose; запущенный `make run` и его том не задевает |
| `make ci` | `make test` и `make smoke` на чистой копии текущего коммита, в отдельном проекте compose и без окружения оболочки. `REPORT=1` записывает итог статусом коммита `ci/local` в GitHub |
| GitHub Actions | Те же `make test` и `make smoke` на Linux x86-64. Запуска может не быть; если он был и упал — PR не готов |

Основная проверка PR — локальная, `make ci`: решение 10 в [DECISIONS.md](../architecture/DECISIONS.md). Она проверяет коммит, а не рабочий каталог: `.env`, незакоммиченные правки и файлы вне git в неё не попадают. Чистая копия кладётся в `.ci/` внутри репозитория, потому что не всякий Docker на macOS видит системный каталог временных файлов, а монтирование невидимого каталога не падает — оно молча оказывается пустым.

Набор должен оставаться быстрым: `make test` запускается перед каждым пушем. Модульные тесты не трогают базу; тесты с базой работают в транзакции, которая откатывается, а те, которым нужна настоящая фиксация — запись и захват сессии, — в отдельной базе, создаваемой на запуск.

Порог покрытия в процентах не задаётся. Мера полноты — принцип 4: каждая строка таблиц гарантий имеет тест.

## Что не тестируется на этом этапе

| Что | Почему |
