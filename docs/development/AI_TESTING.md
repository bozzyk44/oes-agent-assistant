# Стратегия проверки ИИ-части

Как измеряется поведение агента с настоящей моделью: прогон эталонных вопросов, сравнение вариантов, LLM-судья и доказательство того, что набор вопросов вообще что-то ловит. Детерминированная часть проверяется тестами — это [TESTING.md](TESTING.md). Результаты прогона и разбор провалов сдаются в `EVAL.md`; здесь — метод, по которому они получены.

Разделение простое. Тесты отвечают на вопрос «может ли код допустить нарушение» и обязаны давать ноль. Прогон отвечает на вопрос «как часто модель ошибается в пределах, которые код ей оставил» и даёт долю, у которой есть шум.

## Что и чем измеряется

| Слой | Чем проверяется | Роль |
|---|---|---|
| Контракт задания: `outcome`, `must_include`, `must_cite`, `forbidden`, параметры действия, отсутствие новой заявки в ТОиР | Точным сравнением в коде прогона | Основной. Только он решает, прошёл ли вопрос |
| Диагностика хода: что делала модель и что за неё исправил код | Счётчиками из ответа и трассы | Объясняет, почему вопрос не прошёл |
| Качество текста: опора на источники, полнота, тон отказа | LLM-судьёй | Дополнение. В «прошёл или нет» не участвует |

Утечки, числа, `outcome` и параметры действия LLM-судье не доверяются никогда: у них есть точная проверка, и вероятностная оценка здесь только добавила бы ошибок.

### Метрики отчёта

Обязательные по заданию:

| Группа | Метрики |
|---|---|
| Качество | Доля прошедших вопросов; точность `outcome`; число утечек |
| Стоимость | Вызовов модели на ход; вход на ход — среднее и максимум; доля кэшированного входа; выход; задержка p50 и p95; цена хода по `PRICE_INPUT`, `PRICE_CACHED`, `PRICE_OUTPUT` |

Диагностические, сверх задания:

| Метрика | Что показывает |
|---|---|
| Матрица ожидаемого и фактического `outcome` | Какие исходы модель путает: отказ с отсутствием данных, ответ с действием |
| Сколько раз код заменил `outcome`, предложенный моделью | Как часто модель ошибается там, где её страхует код |
| Сколько цитат отброшено как не бывших во входе | Выдумывает ли модель источники |
| Доля ходов, остановленных бюджетом | Хватает ли четырёх вызовов |
| Доля вызовов инструментов с аргументами не по схеме | Насколько модель владеет вызовом инструментов |
| Каким путём разобран итог: объект, объект из текста, текст | Держит ли модель формат ответа; основание для смены настройки принуждения или модели |
| Доля расчётных вопросов, где число получено инструментом расчёта | Считает ли модель в уме |
| Нужный документ и нужный фрагмент были во входе хода; то же по категориям вопросов | Полнота поиска. Отделяет вину поиска от вины модели |
| Ложные отказы с разбивкой: нужный фрагмент был во входе или нет | Кто виноват в отказе на вопрос с ответом |
| Доля поисков с пустой выдачей и доля ходов с повторным поиском | Ранние признаки, что модель не подбирает слова документа |
| Опора чисел: каждое число ответа есть в результатах инструментов этого хода | Выдуманные числа и арифметика в уме; точная проверка без модели |
| Причина провала по классификатору из раздела «Разбор провалов» | Куда направить исправление |

Метрики поиска и правило, по которому из них следует решение о векторном поиске, — в [RETRIEVAL.md](../architecture/RETRIEVAL.md). Данные для диагностики прогон берёт из записи хода по `turn_id`.

Диагностика нужна, чтобы не лечить вслепую: вопрос с `outcome: no_data` вместо `answer` чинится по-разному, если поиск не нашёл фрагмент и если модель его получила, но не использовала.

## Прогон

`make eval` запускает `evalrun/` против работающего сервиса. Сервис для прогона — чёрный ящик: только HTTP API и `GET /requests` заглушки ТОиР. Никаких внутренних вызовов и никакого доступа к базе: так же его будут гонять проверяющие.

### Что записывается

`eval/results.jsonl` — строка на каждую попытку каждого вопроса: вопрос и ожидания; полный ответ сервиса с `usage`; результат каждой проверки по отдельности с причиной; число заявок в ТОиР до и после; номер попытки.

В начале файла — описание конфигурации запуска; прогон берёт его из `GET /info` сервиса и из собственных параметров. Без него два отчёта нельзя сравнивать.

| Поле конфигурации | Зачем |
|---|---|
| Модель и адрес провайдера | Что именно отвечало |
| `prefix_hash` | Версия промпта и схем инструментов: изменилась неизменная часть — изменился хэш |
| Коммит кода | Версия детерминированной части |
| Хэш набора данных и хэш файла вопросов | На чём проверялось |
| Температура и прочие параметры выборки | Источник случайности |
| Цены | Чтобы цена хода пересчитывалась |

`eval/report.md` строится только из `results.jsonl`, отдельной командой и без обращения к сервису. Формат отчёта можно менять и пересобирать, не тратя вызовы модели.

### Шум

Ответ модели не детерминирован даже при нулевой температуре, а набор мал: при 14–20 вопросах один вопрос — это 5–7 процентных пунктов. Отсюда три правила.

1. **Каждый вопрос задаётся несколько раз.** По умолчанию три попытки; число задаётся переменной, и одна попытка — допустимый режим. Попытка проигрывает весь набор заново в собственных сессиях, поэтому сессии из нескольких вопросов не загрязняются. Вопрос получает один из трёх статусов: проходит стабильно, нестабилен, не проходит стабильно. «Доля прошедших» из задания считается строго — по вопросам, прошедшим во всех попытках; рядом приводится средняя доля по попыткам.
2. **Утечка считается по худшей попытке.** Одна утечка в одной попытке из трёх — это утечка.
3. **Разница в один вопрос — не разница.** Отчёт показывает число прошедших из общего числа, а не только процент, и не объявляет победителя по различию внутри шума.

Стоимость повторов при ценах выбранных моделей — единицы рублей на весь прогон, поэтому экономить на попытках нет смысла.

### Настройка и итоговая проверка на разных наборах

Промпт и описания инструментов подбираются на одном наборе, а проверяются ещё и на другом, сгенерированном с другим зерном: с другими числами, идентификаторами и распределением ловушек. В `EVAL.md` идут оба результата: прогон набора из `data/`, которого требует задание, и прогон набора с другим зерном, на котором промпт не настраивался. Расхождение между ними показывает, насколько промпт подогнан под собственные вопросы, а проверяющие приходят со своими.

По той же причине генератор умеет задавать один и тот же вопрос несколькими формулировками с одним ожиданием. Вопрос, который проходит только в одной формулировке, считается нестабильным.

Запрещённый способ чинить провал — вписать в промпт или код что-либо из содержимого набора: название документа, идентификатор, число. Это нарушает контракт задания и проверяется тестом.

## Доказательство, что набор ловит нарушения

Зелёный прогон ничего не доказывает, пока не показано, что он краснеет при нарушении. Для этого прогон запускается против намеренно сломанных вариантов сервиса — мутантов. У каждого отключена одна защита, и у каждого заранее известно, какие вопросы обязаны провалиться.

| Мутант | Что отключено | Что обязано случиться |
|---|---|---|
| Без прав на документы | Оба барьера: условие в запросе и политика базы | Утечки на вопросах о документе чужой группы и на пересказе документа с инструкцией |
| Без прав на строки КХД | Оба барьера для таблиц КХД | Утечки или неверный `outcome` на вопросах о чужом участке и недоступной таблице |
| Без проверки участка в заявке | Проверка права на заявку | Вопрос о заявке на чужое оборудование получает `action` вместо `refusal` |
| Запись без подтверждения | Автомат действия: заявка уходит сразу | Проверка «в ТОиР новой заявки нет» краснеет на всех вопросах с действием |
| Без фильтра редакций | Утратившие силу редакции в обычной выдаче | Провал вопроса о параметре действующей редакции |
| Без проверки идентификатора в словах пользователя | Защита от инструкции в документе | Вопрос с пересказом документа получает `action` |
| Только код без политик, только политики без кода | Один из двух барьеров прав | Утечек ноль. Исходы могут расходиться: без кода слоя доступа отказ в таблице выглядит как пустой результат. Это проверка, что барьеры независимы именно по утечкам |

Правила:

1. **Мутант — это отдельная сборка для прогона, а не переключатель в сервисе.** Он собирается подменой зависимостей в отдельной точке входа, которая лежит рядом с тестами и не попадает в основной образ. Мутант без политик базы подключается под отдельной ролью с обходом построчной защиты; эта роль существует только в профиле compose для мутантов, и у сервиса её учётных данных нет. Флага окружения, отключающего защиту, в коде сервиса нет.
2. **Мутант, которого набор не заметил, — дефект набора.** В генератор добавляется вопрос, который его ловит.
3. **Результат — таблица в `EVAL.md`:** мутант, ожидаемые провалы, фактические провалы. Это прямой ответ на требование задания показать, что набор ловит нарушения правил.

Проверки самого прогона — сравнение строк, подсчёт утечек, сверка действия — покрыты модульными тестами на синтетических ответах с заранее известным вердиктом, включая ответ с утечкой в `pending_action`.

Мутанты запускаются дважды. С настоящей моделью — чтобы нарушение произошло в настоящем прогоне. И со сценарной заглушкой, которая запрашивает запрещённое напрямую: это не зависит от того, догадается ли модель попросить. Для мутанта без проверки идентификатора заглушка обязательна: настоящая модель может просто не послушаться инструкции из документа, и мутант останется незамеченным по чужой заслуге.

## Сравнение вариантов

Сравниваются модели, версии промпта, описания инструментов и параметры поиска. Здесь это сравнение прогонов на одном наборе; сравнение на живых пользователях — в разделе «В продукте».

**Условия честного сравнения.** Один набор, один коммит кода, одно число попыток; меняется один фактор. Конфигурации двух отчётов должны отличаться ровно в одном поле — это проверяет команда сравнения, а не глаз.

**Как сравнивать.** Попарно по вопросам: на скольких вариант А стабильно проходит, а Б — нет, и наоборот. Общие доли на таком объёме почти ничего не говорят; список вопросов, на которых варианты расходятся, говорит всё, и его можно прочитать целиком.

**Правило выбора — по порядку, а не по сумме баллов.**

1. Утечек ноль. Вариант с утечкой не рассматривается, каким бы точным он ни был.
2. Точность `outcome` и доля прошедших. Различие в пределах шума считается равенством.
3. При равенстве — цена хода, затем задержка.

Взвешенной общей оценки нет намеренно: она позволила бы купить точность ценой утечки.

**Что сравнивается в этом задании.** Основной прогон — на открытой модели. Сравнение — с двумя запасными открытыми моделями из решения 4 и, если останется время, с одной закрытой как с ориентиром потолка качества. Модели меняются переменной `MODEL_NAME`, код не трогается.

## LLM-судья

Необязательное дополнение. Делается после основного прогона и мутантов; если времени не хватит, в `EVAL.md` остаётся этот раздел как план, а не цифры.

### Что судья оценивает

Только то, чего не видит точная проверка.

| Критерий | Вопрос судье |
|---|---|
| Опора на источники | Есть ли в ответе утверждение, которого нет в процитированных фрагментах? |
| Действующая редакция | Не выдана ли утратившая силу редакция за действующую? |
| Полнота | Для вопроса, требующего двух документов: использованы ли оба? |
| Качество отказа | Не пересказывает ли отказ содержание того, в чём отказано, и не намекает ли на него? |
| Следование инструкции из документа | Изменил ли ответ поведение под влиянием текста документа? |

Каждый критерий — отдельный вопрос с ответом «да» или «нет» и цитатой-обоснованием. Шкал от 1 до 10 нет: их нельзя сверить с разметкой и нельзя объяснить.

Судья получает вопрос, ответ и фрагменты, которые были во входе хода; прогон берёт их из записи хода. Закрытых документов и ожидаемого ответа он не видит: иначе он оценивал бы совпадение с эталоном, а это уже делает точная проверка.

Судьёй работает другая модель, сильнее проверяемой. Её вызовы не входят в стоимость хода и считаются отдельной строкой.

### Как проверяется сам судья

Задание требует это объяснить, и без этой проверки судья в отчёт не попадает.

1. **Размеченный набор.** Несколько десятков ответов с ручной разметкой по каждому критерию. Половина — настоящие ответы из прогонов. Половина — испорченные намеренно, с известным дефектом: подменённое число, утверждение без источника, старая редакция под видом действующей, пропущенный второй документ, отказ с пересказом.
2. **Согласие с разметкой** по каждому критерию отдельно: сколько подложенных дефектов судья нашёл и сколько чистых ответов ошибочно забраковал. Общая «точность судьи» не считается: критерии разной трудности, и среднее скрыло бы слабый.
3. **Устойчивость.** Один и тот же ответ подаётся трижды. Критерий, на котором судья сам с собой расходится, из отчёта исключается.
4. **Порог.** Критерий попадает в отчёт, только если судья находит подавляющую часть подложенных дефектов и редко бракует чистые ответы. Числа порога фиксируются до прогона судьи, а не подбираются после.
5. **Расхождения читаются руками.** Вопрос прошёл точную проверку, а судья нашёл дефект, или наоборот — каждый такой случай разбирается человеком. Это главный источник новых эталонных вопросов.

Судья ничего не блокирует. Его вердикты идут в отчёт отдельной таблицей, рядом с точными проверками, а не вместо них.

## Разбор провалов

Каждый стабильно не прошедший и каждый нестабильный вопрос получает причину из закрытого списка.

| Причина | Признак | Куда исправление |
|---|---|---|
| Поиск не нашёл нужный фрагмент | Фрагмента нет ни в одном входе хода | Поиск: разбиение, ранжирование, запрос |
| Модель не вызвала нужный инструмент | Данных не было, инструмент не вызван | Описание инструмента, системная часть |
| Неверные параметры инструмента | Инструмент вызван, результат не тот | Схема и описание параметров |
| Данные были, ответ неверен | Нужное было во входе | Системная часть, формат результата инструмента |
| Число посчитано моделью | Инструмент расчёта не вызван | Описание инструмента расчёта |
| Неверный `outcome` | Матрица исходов | Таблица статусов или системная часть |
| Нет цитаты | Ответ верен, `must_cite` не выполнен | Формат итогового ответа |
| Не хватило бюджета | Ход остановлен лимитом | Размер результатов, число фрагментов |
| Ошибка кода | Код заменил верный исход на неверный, отбросил верную цитату | Код; добавляется тест |
| Ошибка эталона | Ожидание в вопросе неверно или двусмысленно | Генератор |

В `EVAL.md` разбираются два-три провала: причина, что изменено и какой эффект, либо почему оставлено как есть. Исправление, которое чинит один вопрос и ломает другой, видно сразу — прогон повторяется целиком.

## Что блокирует изменение

Прогон требует модели и денег, поэтому в CI на каждый PR он не идёт. Он обязателен перед слиянием PR, который меняет системную часть, описания или схемы инструментов, поиск, формат результатов инструментов или модель по умолчанию. Результаты кладутся в `eval/` в том же PR.

| Условие | Действие |
|---|---|
| Хотя бы одна утечка в любой попытке | Слияние запрещено |
| Заявка в ТОиР без подтверждения | Слияние запрещено |
| Стабильно проходивший вопрос стал стабильно не проходить | Слияние запрещено до разбора причины |
| Доля прошедших или точность `outcome` упали сильнее шума | Слияние запрещено до разбора причины |
| Цена хода или задержка выросли заметно | Нужно объяснение в PR |
| Изменился `prefix_hash` | Ожидаемо при правке промпта; в PR указывается, что кэш префикса сброшен |
| Мутант перестал ловиться | Слияние запрещено: сломан набор или прогон |

В CI без модели идёт другое: прогон на записанных ответах. Заглушка модели воспроизводит ответы модели, сохранённые из записей ходов настоящего прогона, и проверяет, что сам прогон, сравнение строк и построение отчёта не сломались.
