# Поиск по документам: почему без векторов, когда они нужны и с чего начинать

Ассистент уже работает по схеме «найти и ответить по найденному»: поиск по документам, затем генерация с цитатами. В этом смысле RAG в решении есть. Чего в нём нет — эмбеддингов, векторного и гибридного поиска, реранкера и переписывания запроса отдельной моделью. Этот документ объясняет, почему их нет сейчас, по каким измеримым признакам их пора добавлять, в каком порядке и что измерять уже сегодня, чтобы это решение было принято по цифрам.

Устройство текущего поиска — в [ARCHITECTURE.md](ARCHITECTURE.md), раздел «Документы и поиск».

Часть выводов опирается на замеры из личного проекта автора [rag-ru-reports](https://github.com/bozzyk44/rag-ru-reports): поиск и ответы по годовым отчётам российских компаний, 22 документа, 4 788 фрагментов, 68 вопросов, 16 конфигураций поиска. Там другой корпус и другой масштаб, поэтому эти выводы здесь — гипотезы с известным направлением, которые надо перепроверить на своих данных, а не установленные факты.

## Почему не сейчас

| Причина | Подробнее |
|---|---|
| Корпус мал | 10–15 документов — это порядка сотни фрагментов. Лексический поиск со стеммингом перебирает их целиком; приближённый векторный индекс на таком объёме ничего не ускоряет и не находит |
| Сервис запускают на чужом наборе без подготовки | Набор проверяющих загружается при старте. Эмбеддинги пришлось бы считать в этот момент: либо локальной моделью — это гигабайты в образе и минуты на процессоре стенда, — либо внешним API, для которого в контракте задания нет переменных. Модель чата проверяющих эмбеддингов может не уметь |
| Вопросы задания — про точные слова | Идентификаторы оборудования, номера приоритетов, моточасы, названия регламентов. Точный токен — сильная сторона лексики и слабая — векторов: в rag-ru-reports на вопросах о числах лексика нашла 94 % против 82 % у векторного поиска, потому что эмбеддинг почти не различает близкие числа |
| Разницу нечем измерить | На 14–20 вопросах один вопрос — это 5–7 процентных пунктов. В rag-ru-reports на 51 вопросе из 16 конфигураций поиска различимы оказались две. Улучшение, которое набор не способен разрешить, — это вера, а не замер |
| Модель уже переформулирует запрос | Агент сам составляет поисковый запрос и может искать повторно, если выдача не подошла. Часть того, что даёт переписывание запроса, получается без отдельного компонента |
| Каждый индекс — ещё одно место для прав | Сейчас условие по группам доступа стоит в том же запросе, что и ранжирование, и продублировано построчной защитой. Второй индекс требует того же, и это надо доказывать отдельными тестами |
| Лимиты стенда | 8 ГБ памяти уже распределены между сервисом, базой и наблюдаемостью |

Ни одна из причин не говорит, что векторный поиск плох. Все они говорят, что на этом корпусе и этом наборе вопросов его польза не будет видна, а цена — будет.

## Когда он оправдан

Решение принимается по признакам, которые видны в прогоне и в работе, а не по размеру корпуса самому по себе: лексический поиск масштабируется на миллионы документов.

| Признак | Откуда берётся | Что он означает |
|---|---|---|
| Причина «поиск не нашёл нужный фрагмент» — самая частая среди провалов | Классификатор провалов в прогоне | Главный признак. Узкое место — поиск, а не модель |
| Вопрос проходит в одной формулировке и не проходит в другой | Вопросы с несколькими формулировками | Лексический разрыв: вопрос и документ называют одно и то же разными словами. Именно здесь векторный поиск сильнее: в rag-ru-reports на вопросах о фактах он нашёл 100 % против 88 % у лексики |
| Растёт доля поисков с пустой выдачей и доля повторных поисков в ходе | Счётчики хода, без разметки | Модель не может подобрать слова документа |
| Корпус стал разнородным | Подключение СЭД заказчика: сотни тысяч документов разных подразделений, синонимы, сокращения, жаргон | Словарь вопроса и словарь документа расходятся систематически |
| Появились документы без структуры и без точных терминов | Письма, протоколы, переписка | Искать приходится по смыслу, а не по термину |

Правило запуска работ: задача на векторный поиск открывается, когда причина «поиск не нашёл нужный фрагмент» лидирует среди провалов в двух прогонах подряд на наборах с разными зёрнами. До этого любое время полезнее потратить на то, что лидирует на самом деле.

Чем это не лечится: неверным выбором инструмента, арифметикой модели, пропущенными цитатами, вопросами по таблицам хранилища. Данные хранилища через текстовый поиск не идут вообще — для них есть структурный запрос.

## С чего начинать

Порядок выбран так, чтобы каждый шаг либо давал измеримый выигрыш, либо отбрасывался с цифрой, и чтобы права на каждом шаге оставались в том же запросе, что и ранжирование.

### Шаг 0. Сначала измеримость

Без этого шага остальные бессмысленны.

1. **Разметка на уровне фрагмента.** Для каждого вопроса — какой фрагмент содержит ответ. `must_cite` даёт только документ.
2. **Набор, способный различить варианты.** Сотни вопросов, а не десятки, с разбивкой по категориям: точный термин, перефразировка, число, две редакции, ответ из двух документов.
3. **Вопросы и разметка не от автора системы.** В rag-ru-reports вопросы, разметку и систему делал один человек, и переделка разметки сдвинула полноту поиска на 13 процентных пунктов; в продукте источник вопросов — продакшн-трассы.
4. **Сравнение попарно по вопросам:** сколько выиграно и сколько проиграно относительно текущего поиска, а не разность средних.

Урок, ради которого шаг стоит первым: измеримость заканчивается раньше, чем инфраструктура.

### Шаг 1. Лексика отбирает кандидатов, векторы их пересчитывают

Эмбеддинг хранится колонкой в той же таблице фрагментов. Лексический поиск с условием по правам отбирает несколько десятков кандидатов, косинусная близость переупорядочивает только их.

| Почему так | |
|---|---|
| Права не меняются | Тот же запрос, то же условие по группам, та же построчная защита. Нового индекса с собственными правами нет |
| Нет приближённого индекса | Точный пересчёт по десяткам векторов — доли миллисекунды при любом размере корпуса |
| Дёшево проверить | Одна колонка и одна сортировка; отбрасывается без следа, если замер не подтвердил |

В rag-ru-reports эта схема на 50 кандидатах дала ту же полноту, что полный векторный перебор по 4 835 фрагментам: ноль выигранных и ноль проигранных вопросов. Ограничение схемы известно заранее: фрагмент, у которого с вопросом нет ни одного общего слова, в кандидаты не попадёт. Если признак «лексический разрыв» при этом остаётся — нужен шаг 2.

### Шаг 2. Два независимых поиска и слияние

Лексический и векторный поиск идут параллельно, списки сливаются. Слияние по рангам — не бесплатное улучшение: в rag-ru-reports оно выиграло 8 вопросов и проиграло 2 при трёх фрагментах во входе, но при пяти не выиграло ни одного и проиграло 3. Результат зависит от того, сколько фрагментов уходит модели, поэтому веса и число фрагментов подбираются на своём наборе.

Векторный индекс на этом шаге должен применять права до отбора ближайших, а не после: фильтрация готового списка опустошает выдачу и по её размеру выдаёт существование закрытого.

### Шаг 3. Реранкер

Только многоязычный и только с замером. Реранкер — компонент, который ошибается уверенно: в rag-ru-reports англоязычная модель поставила наверх верный фрагмент в 2 случаях из 6 на русском. Вывод о классе моделей из этого не следует; следует, что без проверки на своём языке его включать нельзя. Реранкер добавляет задержку каждому поиску и требует своего инференса в контуре.

### Шаг 4. Приближённый индекс

Нужен, когда точный перебор перестаёт укладываться в задержку, — по порядку величины от сотни тысяч фрагментов. До этого он добавляет зависимость и теряет в полноте, ничего не давая взамен.

### Что учитывать на любом шаге

| Практика | Основание |
|---|---|
| Модель эмбеддингов — многоязычная | Англоязычная модель на русском схлопывает шкалу близости: несвязанные тексты похожи друг на друга, порог не выставить. В rag-ru-reports фоновая близость 0,78 против 0,31 у многоязычной |
| Эмбеддинги считаются там же, где живут данные | Требование «данные не покидают Россию» относится к ним так же, как к модели чата |
| Разбиение по структуре документа, а не по длине | Заголовки и таблицы — естественные границы. Шапка таблицы и единицы измерения идут с каждой её частью: в rag-ru-reports 80 % табличных фрагментов сначала не содержали единицы |
| Числа и идентификаторы всегда ищутся лексически | Векторы их размывают; точный токен должен оставаться отдельным сигналом |
| Фильтры по метаданным — только проверенные замером | Фильтр по году документа в rag-ru-reports проиграл 5 вопросов и выиграл 1: год документа — не год данных. Фильтр по статусу редакции у нас — другое дело, он следует из правила задания, а не из догадки о релевантности |
| Составной вопрос — это несколько поисков | Сравнения и ответы из двух документов были худшей категорией в rag-ru-reports и не лечились ни моделью эмбеддингов, ни фильтрами. У агента эта возможность уже есть: он может искать дважды |
| Права проверяются при чтении, а не только при индексации | Права в источнике меняются после индексации; индекс хранит копию, которая устаревает |
| Кэш ответов учитывает права пользователя | Иначе ответ, собранный для одного, уйдёт другому |
| Отрицательный результат остаётся в таблице | Строка «выиграно 2, проиграно 5» полезнее её отсутствия: к варианту не вернутся через месяц |

Что не делается, пока нет измеренной причины: переписывание запроса отдельной моделью, поиск по сгенерированному псевдоответу, несколько формулировок на запрос, графовый поиск, дообучение эмбеддингов без тысяч размеченных пар.

## Что измерять уже сейчас

Эти метрики нужны и без векторного поиска: по ним видно, пора ли его делать, и на них же будет измерен его эффект. Все они — диагностика прогона; на «прошёл или нет» не влияют.

### С разметкой

| Метрика | Как считается | Зачем |
|---|---|---|
| Нужный документ был во входе хода | Документы из `must_cite` среди фрагментов, попавших во вход | Полнота поиска на уровне документа; считается на любом наборе, включая набор проверяющих |
| Нужный фрагмент был во входе хода | По разметке фрагментов из генератора | То же точнее; только на своём наборе |
| То же по категориям вопросов | Точный термин, перефразировка, число, редакции, два документа | Среднее скрывает слабую категорию |
| Ложный отказ: `no_data` или `refusal` на вопрос с ответом | С разбивкой: нужный фрагмент был во входе или нет | Отделяет вину поиска от вины модели. В rag-ru-reports модель отказывалась в 10 % случаев, когда ответ был во входе, и в 80 %, когда его не было: ложный отказ оказался симптомом поиска |
| Устойчивость к формулировке | Доля вопросов, проходящих во всех формулировках | Прямой измеритель лексического разрыва |

### Без разметки

| Метрика | Зачем |
|---|---|
| Доля поисков с пустой выдачей | Ранний признак: модель не подбирает слова документа |
| Доля ходов с повторным поиском | То же, и это прямой расход бюджета вызовов |
| Доля цитат, отброшенных как не бывших во входе | Модель выдумывает источники |
| Точность цитат: процитированный фрагмент действительно содержит то, на что ссылаются | Полнота поиска этого не видит: в rag-ru-reports при одинаковой полноте точность цитат различалась на 18 пунктов между двумя реализациями |
| Опора чисел: каждое число ответа есть в результатах инструментов этого хода | Точная проверка без модели. Число, которого не было во входе, — выдумка или арифметика в уме |
| Токены результатов поиска на ход и число фрагментов во входе | Цена поиска определяется объёмом текста, а не числом вызовов |
| Задержка поиска, p50 и p95 | База для сравнения, когда появится второй этап |

### При замене реализации поиска

Сравнивается выдача по каждому вопросу — пересечение лучших фрагментов старой и новой реализации, — а не только итоговые метрики. В rag-ru-reports две реализации одного алгоритма показали одинаковую полноту при разной выдаче, и за этим стояли три дефекта. Совпадение метрик при разной выдаче не подтверждает ничего.

## Откуда прогон берёт эти данные

Прогон работает с сервисом как с чёрным ящиком, а ответ `POST /turn` по контракту не содержит ни списка фрагментов, попавших во вход, ни статусов инструментов. Диагностика берётся из записи хода: `GET /turns/{turn_id}` отдаёт автору хода вызовы инструментов с параметрами и статусами, идентификаторы фрагментов во входе, путь разбора итога и замены, сделанные кодом. Текста документов и строк хранилища в записи нет — только идентификаторы и счётчики.

Проверяющим эта запись не нужна; она нужна, чтобы отличить «поиск не нашёл» от «модель не использовала» без чтения логов.
