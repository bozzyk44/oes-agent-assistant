# Архитектура детерминированной части

Всё, что в сервисе не является моделью: процессы, модули, хранение, права, запись, бюджет хода и контракт API. Цель документа — показать, какие гарантии задания держит код и в каком именно месте. Почему выбран стек — в [DECISIONS.md](DECISIONS.md); где это развёрнуто — в [INFRASTRUCTURE.md](INFRASTRUCTURE.md).

Принцип один: **модель предлагает, код решает.** Модель выбирает инструмент и формулирует ответ. Что она увидит, сколько раз её вызовут, уйдёт ли запись во внешнюю систему и какой `outcome` получит ход — определяет код.

## Процессы

```
клиент ──HTTP──> сервис ассистента ──HTTPS──> модель (OpenAI-совместимый API)
 (прогон,          │        │
  страница)        │        └──HTTP + Bearer + Idempotency-Key──> заглушка ТОиР ── свой файл SQLite
                   │
                   ├── PostgreSQL: сессии, ходы, сообщения, действия
                   └── DATA_DIR: документы, пользователи, таблицы КХД (только чтение, в памяти)
```

| Процесс | Что делает | Состояние |
|---|---|---|
| Сервис ассистента | API, права, цикл хода, запись | В PostgreSQL. Сам процесс состояния не держит и перезапускается в любой момент |
| Заглушка ТОиР | Принимает и отдаёт заявки | Свой файл SQLite; с сервисом общего хранилища нет |
| PostgreSQL | Изменяемое состояние сервиса | — |

Набор из `DATA_DIR` читается один раз при старте и в базу не переносится: это сменяемый входной контракт, а не состояние сервиса. При нарушении формата сервис не стартует.

## Модули

```
src/assistant/
├── api/        HTTP: маршруты, схемы запросов и ответов, пользователь из заголовка
├── config      настройки из окружения; секрет ТОиР — в отдельном объекте
├── dataset/    чтение и проверка DATA_DIR: документы, пользователи, таблицы
├── access/     права: единственный выход к данным набора
├── tools/      инструменты агента: поиск, документ по ссылке, запрос КХД, подготовка заявки
├── turn/       цикл хода: сборка входа, бюджет, неизменная часть, учёт токенов
├── model/      клиент модели за интерфейсом; заглушка для тестов
├── actions/    конечный автомат действия и клиент ТОиР
├── db/         модели SQLAlchemy, миграции Alembic
└── telemetry/  трассы и журнал вызовов модели
toir_stub/      заглушка ТОиР, отдельное приложение
datagen/        генератор набора: make data
evalrun/        прогон эталонных вопросов: make eval
```

Правила зависимостей, на которых держатся гарантии:

1. **К набору данных ходит только `access/`.** `tools/` и `turn/` получают данные через него и не импортируют `dataset/` напрямую. Правило проверяется тестом на импорты.
2. **Секрет ТОиР знает только `actions/`.** `turn/`, `tools/` и `model/` получают настройки без него, поэтому попасть во вход модели ему неоткуда.
3. **`model/` не знает о правах и бюджете.** Он отправляет готовый вход и возвращает ответ с фактическим расходом. Всё, что должно быть проверено, проверено до него.

## Права

Права применяются в одном месте — в `access/`, до того как данные станут результатом инструмента. Объект доступа создаётся на ход из записи пользователя в `users.json` и не меняется до конца хода.

| Запрос | Что делает `access/` |
|---|---|
| Поиск по документам | Сначала отбирает документы, у которых `acl` пересекается с группами пользователя или содержит `all`, потом ищет только среди них |
| Документ или фрагмент по идентификатору | Проверяет `acl` так же. Нет доступа — ответ «доступа нет» без названия, даты и текста |
| Строки таблицы КХД | Таблицы нет в `kpi` пользователя — «доступа нет». Иначе фильтр по участкам пользователя добавляется к любому запросу и не снимается параметрами |
| Заявка на ремонт | Участок оборудования берётся из `equipment.csv`, а не из слов модели, и сверяется с `repair_requests`. Не совпал — действие не создаётся |

Три следствия:

1. **Запрос к КХД — структура, а не SQL.** Инструмент принимает таблицу, фильтры, группировку и агрегат из закрытого списка: сумма, среднее, минимум, максимум, число строк, длительность интервала. Выполняет запрос код. Модель не может написать условие, которое обойдёт фильтр участка.
2. **Агрегат считается по отфильтрованным строкам.** Запрос «всего по руднику» от начальника одного участка вернёт сумму по его участку и явную пометку, по каким участкам посчитано, а не число по обоим.
3. **Отказ отличается от отсутствия данных.** Инструмент возвращает один из статусов: данные, «доступа нет», «не найдено», «пусто». По ним код отличает `refusal` от `no_data`. Сам факт существования закрытого документа при этом раскрывается — это следует из контракта задания, где для него ожидается `refusal`.

### Документы и редакции

Документ режется на фрагменты по заголовкам `##`; идентификатор фрагмента — `<id документа>#<номер раздела>`. Поиск — лексический, по индексу в памяти, который строится при старте из текущего `DATA_DIR`. Векторного поиска нет: он потребовал бы модель эмбеддингов при каждом запуске на чужом наборе.

Редакции со статусом `superseded` в обычную выдачу не попадают. Если запрос совпал с утратившей силу редакцией, инструмент возвращает действующую по ссылке `superseded_by` и отдельной строкой сообщает, что прежняя редакция существует и заменена.

Текст документа приходит модели как данные: в отдельном блоке результата инструмента, с пометкой источника. Инструкции внутри него на код не влияют по построению — запись без подтверждения невозможна независимо от того, что ответила модель (раздел «Запись»), а закрытый документ не попадает во вход независимо от того, что она запросила.

## Хранение

| Таблица | Что хранит | Ключевое |
|---|---|---|
| `sessions` | Сессия и её владелец | `session_id` — первичный ключ; `user_id` задаётся при первом ходе и не меняется |
| `turns` | Ход: вопрос, `outcome`, ответ, цитаты, расход | Уникальность пары «сессия, номер хода» |
| `messages` | История сессии для следующих ходов | Пишется одной транзакцией в конце хода |
| `actions` | Предложенное действие и его судьба | Статус, ключ идемпотентности (уникальный), `request_id` |

**Сессия принадлежит одному пользователю.** В истории сессии лежат данные, которые видел её владелец. Ход с чужим `session_id` отклоняется с кодом 403 — иначе второй пользователь унаследовал бы чужой контекст в обход прав.

**Ход атомарен.** Сообщения, итог хода и предложенное действие записываются одной транзакцией в конце. Если узел упал посреди хода, в базе остаётся только строка незавершённого хода; история сессии не содержит половины хода, действие не создано, клиент повторяет запрос. Незавершённый ход не возобновляется.

**Два одновременных хода в одной сессии** не допускаются: второй получает 409 по уникальности номера хода.

## Запись

Действие — конечный автомат в таблице `actions`.

```
              подтверждение автором              ответ ТОиР записан
 proposed ───────────────────────> confirming ───────────────────> done
    │                                  ▲   │
    │ отказ автора                     └───┘ повтор подтверждения:
    ▼                                        тот же ключ, тот же запрос
 rejected
```

Подтверждение выполняется в три шага:

1. **Намерение.** В транзакции: проверка, что подтверждает автор; повторная проверка права на участок оборудования; переход `proposed → confirming` условным обновлением «только если статус всё ещё `proposed`». Фиксация.
2. **Вызов.** `POST /requests` в ТОиР с ключом идемпотентности действия. Ключ создан вместе с действием и хранится в той же строке.
3. **Результат.** В транзакции: `confirming → done` и `request_id`. Фиксация.

| Ситуация | Что происходит |
|---|---|
| Подтверждения не было | Шаг 2 недостижим: клиент ТОиР вызывается только из перехода в `confirming` |
| Повторное подтверждение после `done` | Возвращается сохранённый `request_id`, ТОиР не вызывается |
| Падение между шагами 2 и 3 | Статус остался `confirming`. Повторное подтверждение повторяет шаг 2 с тем же ключом, ТОиР возвращает ту же заявку, шаг 3 её записывает |
| Два подтверждения одновременно | Оба могут дойти до ТОиР с одним ключом и получат одну заявку |
| ТОиР не ответил или ответил ошибкой | Статус остаётся `confirming`, клиент получает 502 и может повторить. Назад в `proposed` действие не возвращается: неизвестно, создана ли заявка |
| Подтверждение или отказ другим пользователем | 403, статус не меняется |
| Подтверждение после отказа | 409 |
| Отказ после подтверждения | 409 |

«Ровно один раз» складывается из двух половин: сервис может вызвать ТОиР больше одного раза, но всегда с одним ключом, а ТОиР по одному ключу создаёт одну заявку. Убрать любую половину — гарантия пропадает, поэтому обе покрыты тестами.

**Предложение действия.** Инструмент подготовки заявки проверяет в коде: оборудование существует, его участок разрешён пользователю, приоритет — от 1 до 3. Только после этого создаётся строка в `proposed`, а ход получает `outcome: action`. Сам инструмент ТОиР не вызывает и клиента ТОиР не видит.

**Заглушка ТОиР.** Проверяет `Authorization: Bearer`. По новому ключу создаёт заявку, по известному — возвращает прежнюю с тем же идентификатором. Тот же ключ с другим телом — 409. Уникальность ключа обеспечена ограничением в её базе, а не проверкой в коде.

## Ход

```
запрос ─> пользователь ─> сессия ─> ┌─ сборка входа ─> оценка токенов ─> проверка бюджета ─┐
                                    │                                                      │
                                    └─ результат инструмента ≤ 1 500 <─ права <─ модель <──┘
                                                         │
                          итог: outcome, цитаты, действие ─> одна транзакция ─> ответ
```

### Бюджет

Проверка стоит перед отправкой, а не после ответа.

| Проверка перед каждым вызовом | Лимит |
|---|---|
| Номер вызова в ходе | не больше 4 |
| Оценка входа этого вызова | не больше 8 000 токенов |
| Фактический вход прошлых вызовов хода плюс оценка этого | не больше 24 000 токенов |

Оценку даёт локальный счётчик без сети с запасом; его коэффициент сверяется с фактическим расходом провайдера в прогоне. В `usage` ответа идут только фактические числа.

Если вход не проходит, сборщик сжимает изменяемую часть в фиксированном порядке: сначала старые ходы сессии, потом ранние результаты инструментов этого хода. Не помогло — вызов не отправляется: ход завершается ответом по уже полученным данным, а если их нет — `budget_exceeded`.

Последний разрешённый вызов делается с запретом вызова инструментов, чтобы ход закончился ответом, а не четвёртым запросом данных. Запрет передаётся параметром запроса; схемы инструментов при этом остаются во входе без изменений.

**Результат инструмента** обрезается до 1 500 токенов до попадания во вход. Обрезанный результат несёт явную пометку и ссылку: идентификаторы следующих фрагментов или число оставшихся строк. Продолжение запрашивается тем же инструментом и проходит те же права.

### Неизменная часть входа

Системная часть и схемы инструментов собираются один раз при старте, сериализуются в канонический вид с фиксированным порядком и хэшируются — это `prefix_hash`. В неизменной части нет времени, идентификаторов хода и сессии, имени и прав пользователя. Сведения о пользователе идут первым сообщением изменяемой части.

### Что решает код, а что модель

| Вопрос | Кто решает |
|---|---|
| Какие данные попадут во вход | Код: права и обрезка |
| Какой инструмент вызвать и с какими параметрами | Модель; параметры проверяет код |
| Сколько вызовов и токенов | Код |
| `outcome: action` | Код: только если в этом ходе создано действие |
| `outcome: refusal` и `no_data` | Модель предлагает, код сверяет со статусами инструментов этого хода |
| Цитаты | Модель называет фрагменты; код оставляет только те, что были во входе этого хода |
| Текст ответа | Модель |

## API

Пользователь — из заголовка `X-User-ID`. Заголовка нет или пользователя нет в `users.json` — 401, ход не начинается.

| Маршрут | Успех | Отказы |
|---|---|---|
| `POST /turn` | 200 с `outcome` из контракта, включая `error` и `budget_exceeded` | 401; 403 — чужая сессия; 409 — в сессии уже идёт ход; 422 — неверное тело |
| `POST /actions/{id}/confirm` | 200, `{"status": "done", "request_id": …}` | 401; 403 — не автор; 404 — нет действия; 409 — отклонено; 502 — ТОиР недоступен |
| `POST /actions/{id}/reject` | 200, `{"status": "rejected"}`; повтор — тот же ответ | 401; 403 — не автор; 404; 409 — уже подтверждено |

Ошибка внутри хода — отказ модели, исключение в инструменте — не превращается в 500: ход завершается с `outcome: error`, расход уже сделанных вызовов сохраняется.

Страница для демонстрации — статический файл, который сервис отдаёт сам. Логики прав в ней нет: она показывает только то, что вернул API.

## Где проверяется

| Обязательная проверка задания | Модуль |
|---|---|
| Документ без доступа не попадает во вход — ни поиском, ни по идентификатору | `access/`, `tools/` |
| Строки КХД чужого участка не попадают во вход | `access/` |
| Подтверждение, повтор, чужой пользователь, падение до записи результата | `actions/` |
| Заявка на чужой участок не предлагается и не создаётся | `tools/`, `actions/` |
| Остановка на лимите, потолок входа, размер результата инструмента | `turn/` |
| `TOIR_TOKEN` не встречается во входе модели | `turn/`, `config` |
| `prefix_hash` не меняется | `turn/` |

Тесты смотрят на вход модели, который записала заглушка, а не на текст ответа: утечка — это то, что модель увидела, а не то, что она пересказала. Тесты идут без сети; база на время теста — SQLite в памяти, схема та же.

## Упрощения

| Что упрощено | Как в продукте |
|---|---|
| Набор данных читается в память при старте | Источники подключаются соединителями; права проверяет источник под учётной записью пользователя |
| Незавершённое подтверждение доводит повторный запрос клиента | Фоновый исполнитель или движок долгих процессов доводит его сам |
| Незавершённый ход не возобновляется | Состояние хода сохраняется по шагам |
| Действие не имеет срока жизни | Истечение по времени и отзыв |
| Один процесс сервиса | Несколько узлов; захват сессии блокировкой в базе |
| Поиск лексический | Гибридный, с правами в метаданных индекса |
