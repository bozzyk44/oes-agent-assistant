# Архитектура детерминированной части

Всё, что в сервисе не является моделью: процессы, модули, хранение, права, запись, бюджет хода и контракт API. Цель документа — показать, какие гарантии задания держит код и в каком именно месте. Почему выбран стек — в [DECISIONS.md](DECISIONS.md); где это развёрнуто — в [INFRASTRUCTURE.md](INFRASTRUCTURE.md); как проверяется — в [TESTING.md](../development/TESTING.md).

Принцип один: **модель предлагает, код решает.** Модель выбирает инструмент и формулирует ответ. Что она увидит, сколько раз её вызовут, уйдёт ли запись во внешнюю систему и какой `outcome` получит ход — определяет код.

Состав входа, инструменты глазами модели и формат её ответа — в [AGENT.md](AGENT.md). Здесь зафиксирована граница: что код принимает от модели и как проверяет.

## Процессы

```
клиент ──HTTP──> сервис ассистента ──HTTPS──> модель (OpenAI-совместимый API)
 (прогон,          │        │
  страница)        │        └──HTTP + Bearer + Idempotency-Key──> заглушка ТОиР
                   │ роль сервиса                                      │ роль заглушки
                   ▼                                                   ▼
       ┌─ база сервиса <── миграции, загрузчик (владелец) <── DATA_DIR   база toir ─┐
       └──────────────────────── один сервер PostgreSQL ───────────────────────┘
```

| Процесс | Что делает | Состояние |
|---|---|---|
| Шаги перед сервисом | Три разовых запуска по порядку: роли и базы, миграции, загрузка `DATA_DIR`. Загрузчиком дальше называется третий | Не держат |
| Сервис ассистента | API, права, цикл хода, запись | В PostgreSQL. Сам процесс состояния не держит и перезапускается в любой момент |
| Заглушка ТОиР | Принимает и отдаёт заявки | Своя база `toir` на том же сервере PostgreSQL, своя роль |
| PostgreSQL | Один сервер, две базы: сервиса и заглушки | — |

Сервис подключается к базе под ролью, которая не владеет таблицами и подчиняется построчной защите. Учётных данных владельца у процесса сервиса нет: они есть только у шагов миграций и загрузки. Пароль администратора сервера есть только у шага ролей и баз.

Движок базы в проекте один. Заглушка ТОиР изображает чужую систему, поэтому изолирована так, как была бы изолирована настоящая: отдельная база, отдельная роль, свой секрет подключения и своя фабрика сессий. Роль сервиса не может подключиться к базе `toir`, роль заглушки — к базе сервиса: право подключения отозвано у всех и выдано поимённо. В служебную базу администратора роли приложения тоже не входят. Сервис знает о ТОиР только адрес и токен и общается с ним только по HTTP.

## Запуск

Одна команда — `make run`. Она создаёт `.env` из `.env.example` со случайными секретами, если файла нет, и выполняет `docker compose up`. Прямой `docker compose up` без `.env` останавливается с сообщением, какой переменной не хватает, а не стартует с пустыми секретами.

На машине нужны только Docker и make. Все цели `make` — `data`, `run`, `test`, `eval` — выполняются в контейнерах; Python на хосте не требуется.

| Шаг | Что происходит | Условие перехода к следующему |
|---|---|---|
| 1. PostgreSQL | Стартует сервер | Отвечает по сети, а не только по локальному сокету: во время инициализации образ поднимает временный сервер, которому верить нельзя |
| 2. Роли и базы | Под администратором сервера создаёт роли и базы, если их нет, и при каждом запуске выставляет ролям пароли из окружения | Завершился без ошибки |
| 3. Миграции | Под владельцем доводит схему до последней версии и выдаёт права роли сервиса. Тот же шаг — `make migrate` и шаг деплоя | Завершился без ошибки |
| 4. Загрузчик | Под владельцем читает, проверяет и загружает набор. Миграции не применяет: на отставшей схеме останавливается | Завершился без ошибки |
| 5. Заглушка ТОиР и сервис | Стартуют параллельно | Сервис отвечает на проверку готовности |

Три свойства, от которых зависит запуск на чужой машине:

1. **`DATA_DIR` монтируется в загрузчик с хоста** только на чтение, по умолчанию `./data`. В образ набор не копируется: иначе подмена каталога не подействует.
2. **Роли и базы создаёт шаг запуска, а не сценарии инициализации образа PostgreSQL.** Те выполняются только на пустом каталоге данных, поэтому поверх существующего тома не сработали бы. Шаг идемпотентен и работает одинаково локально, в CI и на стенде. Пароли ролей сервиса, владельца и заглушки выставляются при каждом запуске, а не только при создании: иначе новый `.env` поверх старого тома базы дал бы отказ входа. К паролю администратора это не относится: его сервер запоминает при создании тома, и шаг ролей и баз с новым паролем войти не сможет. Тогда он завершается с подсказкой: вернуть прежний `.env` или удалить том командой `make reset`. База `toir` создаётся с владельцем — ролью заглушки, чтобы та могла создать в ней свою схему.
3. **Модель задаётся тремя переменными** — `MODEL_BASE_URL`, `MODEL_API_KEY`, `MODEL_NAME`. Обязательны адрес и имя; ключ может быть пустым — локальному серверу он не нужен. Они берутся и из `.env`, и из окружения оболочки, из которой запущен compose. Без них сервис стартует, а ход завершается с `outcome: error` и понятной причиной.
4. **Локальная модель на хосте достижима из контейнера.** Адрес вида `localhost` в `MODEL_BASE_URL` указывал бы на сам контейнер, поэтому хост доступен сервису по имени `host.docker.internal`; это записано в README рядом с примером для Ollama.
5. **Прогон читает вопросы с хоста.** В контейнер прогона монтируются каталог файла из `QUESTIONS` и `DATA_DIR` — только на чтение, каталог `eval/` — на запись.
6. **Наружу публикуется только порт сервиса, и по умолчанию — на локальном адресе.** Адрес и порт задают `SERVICE_BIND` и `SERVICE_PORT`. У сервиса нет аутентификации, поэтому открыть его всем — отдельное осознанное действие. PostgreSQL и заглушка ТОиР портов не публикуют: заглушка нужна сервису и прогону, оба работают в сети compose.
7. **Метка вместо секрета останавливает запуск.** Если `.env` скопирован из `.env.example` руками, в переменных остаются метки `__GENERATE__`. Каждый шаг запуска это видит в своих паролях и адресах баз и завершается ошибкой с именами переменных; сервис с паролем-меткой не стартует. Токена ТОиР у загрузчика нет, поэтому метку в `TOIR_TOKEN` проверяют при старте сами сервис и заглушка — вместе со своей конфигурацией; сервис с меткой в `DATABASE_URL` или `TOIR_TOKEN` не стартует, заглушка — с меткой в `TOIR_DATABASE_URL` или `TOIR_TOKEN`.

Образ один на все процессы; сервис, три шага перед ним, заглушка, генератор и прогон отличаются командой запуска. Процессы в контейнерах работают не от суперпользователя.

## Модули

```
src/assistant/
├── api/        HTTP: маршруты, схемы запросов и ответов, пользователь из заголовка
├── config      настройки из окружения; секрет ТОиР — в отдельном объекте
├── ingest/     три шага перед сервисом: роли и базы, миграции, проверка формата DATA_DIR и загрузка
├── access/     права: единственный выход к данным набора
├── tools/      инструменты агента: поиск, документ по ссылке, запрос КХД, расчёт, подготовка заявки
├── turn/       цикл хода: сборка входа, бюджет, неизменная часть, учёт токенов
├── model/      клиент модели за интерфейсом; заглушка для тестов — в tests/
├── actions/    конечный автомат действия и клиент ТОиР
├── db/         модели SQLAlchemy, миграции Alembic с политиками и функциями
└── telemetry/  трассы, метрики и журнал по OTLP: ход, вызовы модели и инструментов, подтверждение
src/toir_stub/  заглушка ТОиР, отдельное приложение
src/datagen/    генератор набора: make data
src/evalrun/    прогон эталонных вопросов: make eval
```

Все четыре пакета лежат в `src/` и не устанавливаются: в образе на `src/` указывает путь поиска модулей.

Правила зависимостей, на которых держатся гарантии:

1. **К данным набора ходит только `access/`.** `tools/` и `turn/` получают данные через него и не обращаются к таблицам набора напрямую. Правило проверяется тестом на импорты.
2. **Секрет ТОиР знает только `actions/`.** Приложение читает его из окружения при старте и держит отдельным объектом, который передаётся только туда. `turn/`, `tools/` и `model/` получают настройки без него, поэтому попасть во вход модели ему неоткуда.
3. **`model/` не знает о правах и бюджете.** Он отправляет готовый вход и возвращает ответ с фактическим расходом. Всё, что должно быть проверено, проверено до него.

## Хранение

Три схемы — по тому, чьи это данные в продукте.

| Схема | Что это в продукте | Таблицы | Кто пишет |
|---|---|---|---|
| `kb` | Индекс документов из СЭД | Реестр идентификаторов документов; фрагменты с текстом, полнотекстовым индексом, группами доступа, статусом и ссылками редакций | Загрузчик |
| `dwh` | Внешнее хранилище данных заказчика | `production`, `downtime`, `equipment` — колонки как в CSV | Загрузчик |
| `app` | Собственные данные приложения | Пользователи и их полномочия; сессии, ходы, сообщения, действия; версия набора | Загрузчик — пользователей и полномочия; сервис — состояние |

### Загрузка набора

Загрузчик считает хэш содержимого `DATA_DIR`. В хэш входит и версия алгоритма загрузки — правила разбиения на фрагменты и индексации: при их изменении набор перезагружается, даже если файлы те же. Если хэш совпал с записанным в `app` — ничего не делает. Если отличается — одной транзакцией заменяет содержимое `kb`, `dwh`, пользователей и полномочий и очищает сессии, ходы, сообщения и действия.

**Миграции — отдельный шаг.** Применение миграций не спрятано в загрузчик: это свой разовый запуск со своим сервисом compose, одинаковый локально, в CI и при деплое; решение 11 в [DECISIONS.md](DECISIONS.md). `docker compose up` и `make run` выполняют его сами, между ролями и загрузкой набора; `make migrate` выполняет его отдельно, и повтор ничего не меняет. Загрузчик набора сверяет версию схемы с последней и на отставшей базе останавливается с подсказкой, а не доводит схему сам: схему меняет ровно одно место. На время миграции шаг берёт блокировку в базе: два одновременных запуска идут по очереди, и второй видит схему уже доведённой.

**Порядок внутри загрузки.** Набор читается и проверяется до любых изменений данных в базе: при ошибке формата данные не меняются. Роли и схема к этому моменту уже доведены предыдущими шагами — они от набора не зависят, и набор с ошибкой формата их не откатывает.

**База новее кода.** Если версии схемы из базы нет среди миграций сборки — базу мигрировала более новая сборка, — шаг миграций и загрузчик останавливаются с этим сообщением, а не советуют применить миграции. Права роли сервиса на таблицы и функции выдаёт шаг миграций при каждом запуске, а не сама миграция: имя роли приходит из окружения, и миграции незачем его знать. Политики построчной защиты имя роли не называют: они действуют на всех, кроме владельца таблиц.

**Смена имён ролей поверх существующего тома.** Если в `.env` сменили имя роли сервиса, прежняя роль теряет право подключения к базе: вход по старой учётной записи закрыт. Если сменили имя владельца, шаг ролей и баз останавливается с подсказкой вернуть прежнее имя или удалить том: объекты базы принадлежат прежней роли, и продолжать молча значило бы оставить ей доступ.

**Что загрузчик проверяет.** Только то, без чего набор нельзя загрузить: наличие файлов документов, пользователей и трёх таблиц; заголовки и типы колонок CSV; обязательные поля frontmatter; совпадение `id` с именем файла; формат дат и времени. При нарушении загрузчик завершается ошибкой с указанием файла и строки, и сервис не стартует.

**Что он прощает.** Набор может быть собран подстановкой в шаблон без оглядки на YAML. Название с двоеточием или решёткой читается целиком — в остальных полях хвост ` # …` остаётся комментарием YAML; `acl` через запятую без скобок — список; пустой `acl` — документ, не доступный никому; `null` в необязательном поле пользователя — то же, что отсутствие поля. Файл в `docs/` без frontmatter — не документ набора: он пропускается и называется в выводе загрузчика. Файл с полем `id`, но без открывающей строки `---` — испорченный документ, и это ошибка.

**Чего он не проверяет.** Состав набора — число профилей, документов, строк, наличие ловушек — проверяет только генератор в `make data`. Загрузчик принимает любые значения групп, участков, причин простоя и типов оборудования, пропускает неизвестные поля и не читает `questions.jsonl`: файл вопросов в хэш не входит. Строки таблиц КХД не обязаны быть уникальными: у каждой таблицы свой ключ строки. Frontmatter разбирается как YAML, поэтому список `acl` может быть записан и в строку, и по элементу на строке. Значения читаются как текст, без угадывания типов: идентификатор `0012` остаётся идентификатором, а не числом. Целые числа таблиц КХД проверяются на границы колонок базы. Набор проверяющих не обязан быть похож на наш ничем, кроме формата.

Два следствия перезагрузки по хэшу:

1. **Подмена набора не оставляет старых данных.** Проверяющий подставляет свой `DATA_DIR` поверх существующего тома базы и получает ответы только по своему набору.
2. **Смена набора — это новая установка.** Сессии очищаются, потому что история хранит данные прежнего набора. Перезапуск с тем же набором состояние сохраняет, включая действия в ожидании подтверждения.

### Пользователи и полномочия

Аутентификация и авторизация разделены. Кто пользователь — сообщает внешний источник: в продукте SSO заказчика, здесь доверенный заголовок `X-User-ID`. Что ему разрешено — хранит приложение.

| Таблица | Что хранит | Источник в `users.json` |
|---|---|---|
| `app.users` | Идентификатор, ФИО, должность | `user_id`, `name`, `position` |
| `app.user_groups` | Группы пользователя для доступа к документам | `groups` |
| `app.kpi_grants` | Пользователь, таблица КХД, участок | `kpi` |
| `app.repair_grants` | Пользователь, участок | `repair_requests` |

`users.json` здесь — способ первичного наполнения этих таблиц, а не то, что сервис читает при каждом запросе. Роль сервиса читает полномочия, но не может их изменить.

### Состояние

| Таблица | Что хранит | Ключевое |
|---|---|---|
| `app.sessions` | Сессия, её владелец, отметка занятости | Первичный ключ — пара «пользователь, `session_id`» |
| `app.turns` | Завершённый ход: вопрос, `outcome`, ответ, цитаты, расход и запись хода для диагностики | Пишется в конце хода |
| `app.messages` | История сессии для следующих ходов, с идентификаторами фрагментов, которые в ней были | Пишется в конце хода |
| `app.actions` | Предложенное действие и его судьба | Статус, ключ идемпотентности (уникальный), `request_id` |
| `app.token_calibration` | Поправка оценки токенов для каждой модели | Первичный ключ — имя модели; множитель от одного до двух и только растёт. Построчной защиты нет: это не данные пользователя |

**Сессия принадлежит одному пользователю.** Ключ сессии — пара «пользователь, `session_id`». Один и тот же `session_id` у двух пользователей — две разные сессии: второй не наследует историю первого, и отказывать ему не в чем. В истории сессии лежат только данные, которые видел её владелец.

**Ход атомарен.** Ход, его сообщения и предложенное действие записываются одной транзакцией в конце. До этого в базе от хода есть только отметка занятости сессии. Если узел упал посреди хода, история не содержит половины хода, действие не создано, клиент повторяет запрос. Незавершённый ход не возобновляется.

**Автомат действия держит и база.** Переходы статуса действия проверяет триггер таблицы: недопустимый переход, создание действия не в статусе `proposed`, правка параметров или ключа идемпотентности и любое обновление без смены статуса отклоняются с ошибкой, какой бы код их ни запросил. Гонку двух одновременных подтверждений закрывает код: строка действия читается с блокировкой, все обновления условные, и второе подтверждение, дождавшись первого, видит `confirming` и повторяет вызов ТОиР с тем же ключом — получает ту же заявку. Триггер — страховка от безусловного обновления в коде: оно не прошло бы молча. Условное обновление в коде остаётся первой проверкой — оно даёт осмысленный ответ клиенту; триггер — вторая. Ключ идемпотентности и время создания ставит база, что бы ни передал код: ключ для вызова ТОиР читается только из строки действия, а не из того, что было в памяти при вставке. Сообщение и действие ссылаются на ход вместе с его сессией и владельцем: автор действия — всегда автор хода.

**Проверка пользователя.** Перед ходом сервис ищет идентификатор из заголовка в `app.users`; транзакции с данными открываются только одним способом — с привязкой к пользователю первым же действием. Если база недоступна уже на этом шаге, `POST /turn` отвечает по контракту с `outcome: error`, а не кодом 500.

**Одна сессия — один ход одновременно.** Ход начинается с захвата сессии: условное обновление ставит отметку «занята до» и случайную метку захвата, если сессия свободна или прежний срок истёк. Не удалось — 409. Завершающая транзакция снимает отметку и проходит, только если метка захвата всё ещё своя: ход, переживший свой срок, ничего не запишет поверх чужого. При ошибке внутри хода отметка снимается сразу, а не по сроку. У хода есть общий предел времени короче срока отметки — `TURN_TIMEOUT_SECONDS` и `SESSION_LEASE_SECONDS`, сервис с пределом не короче срока не стартует; отметка упавшего процесса истекает сама и не блокирует сессию навсегда.

## Права

Права держат два независимых барьера. Первый — код: `access/` проверяет полномочия и строит запрос. Второй — база: построчная защита отдаёт роли сервиса только строки, разрешённые текущему пользователю. Ошибка в одном барьере не становится утечкой, пока цел второй.

### Барьер в коде

Объект доступа создаётся на ход из полномочий пользователя в `app` и не меняется до конца хода.

| Запрос | Что делает `access/` |
|---|---|
| Поиск по документам | Условие по группам доступа стоит в самом запросе поиска: ранжируются только разрешённые фрагменты |
| Документ или фрагмент по идентификатору | То же условие. Нет доступа — «доступа нет» без названия, даты и текста |
| Строки таблицы КХД | Нет полномочий на таблицу — «доступа нет», запрос не выполняется. Иначе условие по участкам пользователя добавляется к любому запросу и не снимается параметрами |
| Заявка на ремонт | Участок оборудования берётся из базы, а не из слов модели, и сверяется с `app.repair_grants`. Не совпал — действие не создаётся |

### Барьер в базе

В начале каждой транзакции сервис сообщает базе идентификатор пользователя — параметром с областью действия «до конца транзакции», переданным как значение, а не подстановкой в текст запроса. Участки и группы база берёт из таблиц полномочий сама; сервис не может передать ей расширенный список.

| Таблицы | Политика для роли сервиса |
|---|---|
| `dwh.production`, `dwh.downtime`, `dwh.equipment` | Видна строка, если у текущего пользователя есть полномочие на эту таблицу и участок строки |
| `kb` — фрагменты | Виден фрагмент, если его группы доступа содержат `all` или пересекаются с группами текущего пользователя |
| `app.sessions`, `app.messages`, `app.turns` | Видна строка, если сессия принадлежит текущему пользователю |

Параметр не задан или пуст, либо такого пользователя нет в `app.users`, — политики не отдают ни одной строки, включая фрагменты документов для всех: забытая привязка к пользователю даёт пустой результат, а не полный. Пустое значение проверяется явно: после первой транзакции на соединении из пула незаданный параметр читается как пустая строка, а не как отсутствие.

Действия построчной защитой не закрыты: проверку «подтверждает автор» с ответом 403 делает код, и ему для этого нужно видеть чужое действие. Текста ответов в строке действия нет — только параметры заявки.

Четыре выборки намеренно идут мимо политик через функции базы. Каждая возвращает одно значение без содержимого, выполняется с правами владельца, имеет фиксированный путь поиска схем и доступна только роли сервиса.

| Функция | Что возвращает | Зачем |
|---|---|---|
| Существует ли документ | Да или нет по реестру идентификаторов | Отличить «доступа нет» от «не найдено» при запросе по идентификатору |
| Написание оборудования | Идентификатор в написании набора: точное совпадение, иначе единственный идентификатор с тем же ключом — без регистра, пробелов (включая неразрывные), дефисов и тире, с приведением похожих букв. Ключ общий у двух идентификаторов — ничего | Модель пишет идентификатор из русского вопроса кириллицей или без дефиса; строки и заявка берутся по написанию из набора. Неоднозначный ключ не находит ни один: первый попавшийся мог бы оказаться на чужом участке |
| Участок оборудования | Код участка оборудования, найденного так же | Право на заявку задаётся отдельно от права на таблицу КХД: пользователь может оформлять заявки, не видя таблицы оборудования |
| Закрыто ли лучшее совпадение | Да или нет: принадлежит ли лучший по рангу фрагмент среди всех документов тому, которого пользователь не видит | Отличить «ответ лежит в закрытом документе» от «ответа нет» при поиске |

Функция «Закрыто ли лучшее совпадение» — осознанный компромисс. Задание требует `refusal` на вопрос о документе чужой группы, а отфильтрованный поиск вернёт по такому вопросу нерелевантные доступные фрагменты, неотличимые от обычного «подходящего нет». Функция отвечает одним битом и не зависит от того, пуста ли доступная выдача. Она сужена так, чтобы по ней нельзя было подбирать числа: слова с цифрами в сравнении не участвуют, поэтому оклад или сумму перебором не найти; совпадение одного слова признаком не считается; пользователю, которого нет в `app.users`, функция не отвечает. Остаточный канал назван прямо: функция раскрывает, что закрытый документ на некую тему существует, — это раскрывает и сам `refusal` — и, сверх того, позволяет тому, кто знает одно слово закрытого фрагмента, проверить, стоит ли рядом другое слово без цифр. Сузить его дальше — задача поиска: отрыв закрытого фрагмента по рангу и доля совпавших слов запроса.

Результаты функций использует код. Во вход модели попадает только статус инструмента.

### Статусы инструментов и `outcome`

Каждый инструмент возвращает статус. Различие между отказом и отсутствием данных создаёт код, а не догадка модели.

| Статус | Когда |
|---|---|
| `ok` | Данные есть и разрешены |
| `denied` | Документ по идентификатору закрыт. Нет полномочий на таблицу КХД. Все участки, явно названные в запросе, вне полномочий. Фильтр по идентификатору оборудования указывает на оборудование чужого участка. Оборудование на участке без права на заявку |
| `not_found` | Документа или оборудования с таким идентификатором нет |
| `empty` | Запрос разрешён, строк или фрагментов нет |
| `needs_identifier` | Подготовка заявки: в сообщении пользователя нет идентификатора оборудования |
| `invalid` | Аргументы вызова не прошли схему или значение не сводится к допустимому: колонка, операция, тип, граница целого, код участка, число в расчёте без источника |

Поиск, кроме статуса, несёт признак «лучшее совпадение закрыто». Отдельный статус для этого не годится: поиск через «или» почти всегда возвращает какие-то доступные фрагменты, и по пустоте выдачи отказ от отсутствия не отличить. Модель получает признак пометкой без содержимого.

Если в запросе к КХД явно названы и разрешённые, и запрещённые участки, инструмент возвращает `ok` по разрешённым и отдельным полем перечисляет участки, в которых отказано. Если участки не названы — считает по всем разрешённым и перечисляет, по каким посчитано: «всего по руднику» от начальника одного участка — это сумма по его участку с явной пометкой, а не число по обоим. Чужой участок, не названный явно, распознаётся только по идентификатору оборудования в фильтре; пустой результат по другим фильтрам остаётся `empty`, чтобы законное «у вас таких строк нет» не превращалось в отказ. Оборудование в фильтре разбирается так же, как участки: всё названное — с чужих участков — `denied`; всё неизвестно базе — `not_found`; смешанный список — данные по своему и отдельное поле с отказанными идентификаторами. Участок оборудования код берёт функцией базы, а не из строк таблицы, которых пользователь может не видеть. Модель переносит коды и идентификаторы из русского вопроса, поэтому сравниваются они без учёта регистра и крайних пробелов, с приведением похожих кириллических букв к латинским; идентификатор оборудования — ещё и без пробелов (включая неразрывные), дефисов и тире внутри, по ключу, который считает база; по ключу он находится, только если ключ однозначен, а строки берутся по написанию из набора. Чужое оборудование, написанное кириллицей, остаётся отказом, а не «такого нет». Названный участок, который не сводится ни к одному коду из полномочий, — `invalid` с перечнем всех кодов участков: опечатка в своём участке не становится отказом, а модель, повторив вызов с чужим кодом, получит `denied`.

Код сводит ход к двум признакам:

| Признак | Когда есть |
|---|---|
| Сигнал отказа | `denied` от любого инструмента; признак закрытого лучшего совпадения; отказ по части участков |
| Использованные данные | В ответе есть принятая цитата или `query_kpi` вернул `ok`. Расчёт и поиск без цитаты не считаются |

Итоговый `outcome` определяется одной таблицей сверху вниз. Она одна для обоих путей разбора ответа; «исход не назван» — это текстовый путь из [AGENT.md](AGENT.md).

| № | Условие | `outcome` |
|---|---|---|
| 1 | В ходе создан черновик действия | `action` |
| 2 | Подготовка заявки вернула `denied` | `refusal` |
| 3 | Есть сигнал отказа, использованных данных нет | `refusal`, что бы ни предложила модель |
| 4 | Есть сигнал отказа и использованные данные | Модель предложила `refusal` или `no_data` — `refusal`; иначе `answer` |
| 5 | Сигнала отказа нет, модель предложила `refusal` | Есть принятая цитата, запрос к КХД либо документ по идентификатору вернул `ok`, `empty` или `not_found` — `no_data`; иначе `refusal`. Поиск без цитаты не в счёт, и пустой тоже |
| 6 | Сигнала отказа нет, модель предложила `no_data` | `no_data` |
| 7 | Сигнала отказа нет, модель предложила `answer` | `answer` |
| 8 | Сигнала отказа нет, исход не назван | Использованных данных нет и ни один инструмент не вернул `ok` — `no_data`; иначе `answer` |

`budget_exceeded` и `error` ставит только код.

Три строки требуют пояснения. Строка 3: модель не может выдать ответ там, где ей во всём отказано. Строка 4: если лучшее совпадение закрыто, а ответ нашёлся в доступном документе и процитирован, он остаётся ответом. Строка 5: полномочия пользователя есть во входе, и модель вправе отказать, не вызывая инструмент; отказ после того, как данные были получены или законно отсутствовали, — это отсутствие данных, а не отказ. Пустой поиск законным отсутствием не считается: признак закрытого совпадения не видит слов с цифрами и одиночных слов, и вопрос о закрытом документе по его идентификатору дал бы пустую выдачу без сигнала отказа.

### Запрос к КХД и расчёты

Инструмент принимает структуру, а не SQL: таблицу, фильтры, группировку и агрегат из закрытых списков. SQL строит код из проверенных частей; модель не может написать условие, которое обойдёт фильтр участка.

| Часть запроса | Что допускается |
|---|---|
| Фильтры | Равенство и вхождение в список по любой колонке; сравнение и диапазон по числам и датам |
| Агрегаты | Сумма, среднее, минимум, максимум, число строк |
| Производные колонки | Моточасы после последнего ППР; длительность простоя в часах |
| Группировка | По любой колонке таблицы и по дате |
| Округление | Число знаков — параметр запроса; округление «половина вверх», одинаковое в запросе и в инструменте расчёта |

Простой попадает в период, если пересекается с ним; в длительность идёт только часть внутри периода. Интервал через полночь при запросе за сутки делится между сутками. Способ расчёта возвращается вместе с результатом.

**Арифметику модель не выполняет.** Проценты, отношения, разности и формулы из нескольких действий считает отдельный инструмент расчёта: модель передаёт числа из результатов и операцию или выражение из чисел, четырёх действий и скобок, код возвращает значение с заданным числом знаков. Выражение разбирается синтаксическим деревом с белым списком узлов и не исполняется. Сравнение в прогоне идёт по точной строке, и число, посчитанное моделью, — источник случайных провалов. Входы расчёта код сверяет с источниками: число, которого нет в результатах инструментов этого хода и в сообщении пользователя, — `invalid`; правило и единственная постоянная без источника — в [AGENT.md](AGENT.md), «Результат инструмента».

### Документы и поиск

**Фрагменты.** Документ режется по заголовкам `##`; текст до первого заголовка — отдельный фрагмент. Раздел длиннее потолка делится на части по абзацам и строкам таблиц; потолок — четверть лимита результата инструмента: в одну выдачу поиска помещается до четырёх фрагментов целиком, остальные доступны по ссылке. Загрузчик меряет потолок в символах, из расчёта три символа на токен — с запасом к измеренным на русском тексте 3,9–4,7; шапка таблицы повторяется в каждой её части. Потолок важнее шапки: таблица, у которой шапка или строка в него не помещается, делится как обычный текст. Идентификатор — `<id документа>#<номер раздела>`, у частей длинного раздела добавляется номер части через точку: `D03#3.2`. Текст до первого заголовка — раздел 0; строка названия `# …` в него не входит. Название документа и заголовок раздела входят в индекс каждого фрагмента.

**Поиск.** Полнотекстовый, средствами PostgreSQL. Слова запроса приводятся к основе русским стеммером; это стемминг, а не морфологический разбор. Запрос — объединение слов через «или» с ранжированием и отбором лучших: требование всех слов сразу давало бы пустую выдачу на обычный вопрос. Буква «ё» приводится к «е» при индексации и в запросе. Идентификаторы и числа — `XY-7`, `ЖК-10` — индексируются отдельно, без стемминга, и ищутся точным совпадением; похожие кириллические буквы в них приводятся к латинским — «ХУ-7», набранный кириллицей, находит «XY-7», — а пробелы и тире внутри не убираются. Векторного поиска нет; почему, когда он понадобится и с чего начинать — в [RETRIEVAL.md](RETRIEVAL.md).

**Редакции.** По умолчанию в выдачу попадают только действующие. Если запрос совпал с утратившей силу редакцией, инструмент возвращает действующую по ссылке `superseded_by` и сообщает, что есть прежняя редакция. Прежняя редакция выдаётся только по явному признаку в запросе и с пометкой «утратил силу, заменён на …» в каждом фрагменте. Права проверяются по `acl` самой запрошенной редакции: о существовании прежней редакции пользователь узнаёт, только если она ему доступна.

**Данные — не инструкции.** Текст документа приходит модели в отдельном блоке результата инструмента с пометкой источника. Три следствия держит код, а не промпт: закрытый документ не попадает во вход независимо от того, что запросила модель; запись без подтверждения невозможна независимо от того, что она ответила; действие не создаётся по тексту документа (раздел «Предложение действия»).

## Запись

Действие — конечный автомат в таблице `app.actions`.

```
              подтверждение автором              ответ ТОиР записан
 proposed ───────────────────────> confirming ───────────────────> done
    │                                │  ▲   │
    │ отказ автора     ТОиР отверг   │  └───┘ повтор подтверждения:
    ▼                  запрос        ▼        тот же ключ, тот же запрос
 rejected                          failed
```

### Предложение действия

Инструмент подготовки заявки проверяет в коде и возвращает черновик или статус отказа:

1. В текущем сообщении пользователя есть идентификатор оборудования — отдельным словом или несколькими словами подряд («XY 7»), а не частью другого идентификатора: слова, склеенные дефисом, — одно слово. Сравнение — по тому же ключу, что в базе: без учёта регистра, пробелов (включая неразрывные), дефисов и тире, с приведением похожих кириллических и латинских букв. Нет — `needs_identifier`, и модель просит назвать идентификатор.
2. Оборудование существует, иначе `not_found`.
3. Участок оборудования разрешён пользователю, иначе `denied`.
4. Приоритет — целое от 1 до 3; описание — непустое, до 10 000 символов, без нулевого символа и одиночных суррогатов; идентификатор от модели — до 200 символов. Иначе `invalid`: черновик, который ТОиР отвергнет как неверный, после подтверждения ушёл бы в `failed`.

В параметры действия идёт идентификатор в том написании, в каком он хранится в базе, а не в том, как его написала модель или пользователь.

Первая проверка закрывает инъекцию: инструкция «оформи заявку на …» в тексте документа не становится действием, потому что идентификатор пришёл не из сообщения пользователя. Область проверки — одно текущее сообщение, а не вся сессия: иначе идентификатор, упомянутый в прошлом вопросе, разрешал бы заявку по инструкции из документа в следующем. Цена — просьба «оформи на него заявку» после разговора об оборудовании требует назвать идентификатор ещё раз.

После успешного черновика ход завершается без следующего вызова модели: `outcome: action`, текст ответа формирует код по шаблону. Строка действия в статусе `proposed` записывается завершающей транзакцией хода: если она не прошла, действия нет и клиент его идентификатора не получил. В одном ходе — не больше одного действия. Инструмент ТОиР не вызывает и клиента ТОиР не видит.

### Подтверждение

1. **Намерение.** В транзакции: проверка, что подтверждает автор; повторная проверка полномочия на участок оборудования; переход `proposed → confirming` условным обновлением «только если статус всё ещё `proposed`». Фиксация.
2. **Вызов.** `POST /requests` в ТОиР с ключом идемпотентности действия. Ключ создан вместе с действием и хранится в той же строке.
3. **Результат.** В транзакции: `confirming → done` и `request_id`. Фиксация.

| Ситуация | Что происходит |
|---|---|
| Подтверждения не было | Шаг 2 недостижим: клиент ТОиР вызывается только из перехода в `confirming` |
| Повторное подтверждение после `done` | Возвращается сохранённый `request_id`, ТОиР не вызывается |
| Падение между шагами 2 и 3 | Статус остался `confirming`. Повторное подтверждение повторяет шаг 2 с тем же ключом, ТОиР возвращает ту же заявку, шаг 3 её записывает |
| Два подтверждения одновременно | Оба могут дойти до ТОиР с одним ключом и получат одну заявку |
| ТОиР недоступен, не ответил вовремя, ответил ошибкой сервера или отказом в авторизации | Статус остаётся `confirming`, клиент получает 502 и может повторить. Назад в `proposed` действие не возвращается: неизвестно, создана ли заявка |
| ТОиР отверг запрос как неверный: 400, 409 или 422 | `confirming → failed`, причина сохраняется. Клиент получает 502; повтор возвращает тот же ответ без вызова ТОиР |
| Полномочие на участок отозвано к моменту подтверждения | 403, статус не меняется |
| Полномочие отозвано после намерения, к повтору из `confirming` | Повтор доводит уже разрешённое намерение с тем же ключом: заявка, возможно, создана прошлой попыткой, и отказ оставил бы её незаписанной, а действие — в `confirming` навсегда. Здесь полномочия меняются перезагрузкой набора, которая удаляет и действия; в продукте, где права отзывают на ходу, повтор после отзыва должен сначала сверяться с ТОиР по ключу и не создавать заявку, если прошлая попытка её не создала |
| Подтверждение или отказ другим пользователем | 403, статус не меняется |
| Подтверждение после отказа | 409 |
| Отказ после подтверждения | 409 |

«Ровно один раз» складывается из двух половин: сервис может вызвать ТОиР больше одного раза, но всегда с одним ключом, а ТОиР по одному ключу создаёт одну заявку. Убрать любую половину — гарантия пропадает, поэтому обе покрыты тестами.

### Заглушка ТОиР

`POST /requests` и `GET /requests` требуют `Authorization: Bearer`. Проверки идут по порядку: токен, ключ, тело — неразборчивый JSON без токена получает 401, а не 422. По новому ключу заглушка создаёт заявку, по известному — возвращает прежнюю с тем же идентификатором. Тело — `equipment_id` от 1 до 200 символов, `description` от 1 до 10 000 символов, `priority` — целое от 1 до 3, без лишних полей; текст без нулевого символа и одиночных суррогатов.

| Случай | Ответ |
|---|---|
| Новый ключ | 201, заявка с `request_id` |
| Известный ключ, то же тело | 200, та же заявка |
| Известный ключ, другое тело | 409 |
| Нет `Idempotency-Key`, он длиннее 200 символов или с нулевым символом — и в `POST`, и в фильтре `GET` | 400 |
| Тело не по схеме, в том числе текст, который база не сохранит | 422 |
| Нет токена или он неверный | 401 |

`GET /requests` отдаёт все заявки по порядку создания вместе с ключами, с параметром `idempotency_key` — только заявку с этим ключом. Тесты смотрят заявку по ключу; прогон ключа действия не знает и сравнивает полный список до вопроса и после.

Уникальность ключа обеспечена ограничением в таблице, а не проверкой в коде. Вставка идёт с условием «при конфликте ключа ничего не делать»: из двух одновременных запросов с одним ключом второй ждёт фиксации первого, ничего не вставляет и возвращает уже созданную заявку, а не ошибку сервера. Схему в базе `toir` заглушка создаёт сама при старте, под своей ролью.

```
запрос ─> пользователь ─> захват сессии ─> ┌─ сборка входа ─> оценка ─> проверка бюджета ─┐
                                           │                                               │
                                           └─ результат ≤ 1 500 <── права <── модель <─────┘
                                                         │
                          итог: outcome, цитаты, действие ─> одна транзакция ─> ответ
```

### Бюджет

Проверка стоит перед отправкой, а не после ответа.

| Проверка перед каждым вызовом | Лимит |
|---|---|
| Номер вызова в ходе | не больше 4 |
| Оценка входа этого вызова | не больше 8 000 токенов |
| Фактический вход прошлых вызовов хода плюс оценка этого | не больше 24 000 токенов |

**Оценка токенов.** Счётчик работает без сети и без словаря токенизатора: модель проверяющих неизвестна, а библиотеки точного подсчёта загружают словари из сети при первом вызове. Оценка строится по символам всего запроса — системной части, схем инструментов, сообщений и служебных накладных на каждое сообщение. Символы считаются по классам: буквы дешевле, цифры, знаки и разметка дороже, потому что в строках таблиц токенов на символ заметно больше, чем в тексте. Коэффициенты задаются настройкой `MODEL_TOKEN_CHARS` и по умолчанию намеренно завышают оценку: проба 2026-10-14 на трёх моделях роутера дала оценку выше факта на тексте документа и на строках хранилища в JSON, а на системной части со схемами инструментов — вчетверо выше факта. Завышение стоит запаса только в текущем вызове: прошлые вызовы идут в бюджет хода фактическими числами. После каждого вызова оценка сверяется с фактическим входом из ответа провайдера, и коэффициенты поправляются только в сторону увеличения; поправка — один множитель на модель, не больше двух, хранится в `app.token_calibration` и переживает перезапуск (решение 12). Нулевой или отрицательный расход в ответе считается отсутствующим. Если сервер не вернул расход, фактом считается оценка, и это помечается в записи хода. В `usage` ответа идут фактические числа.

**Что ограничивает первый вызов.** Длина сообщения пользователя ограничена настройкой; длиннее — 422. История сессии проходит ту же проверку бюджета, что и всё остальное. Остаточный риск назван прямо: у модели с необычно дробным токенизатором вызов может превысить потолок раньше, чем сработает поправка. Такой случай не скрывается — фактическое число попадает в `max_call_input_tokens`.

**Если вход не проходит.** Сборщик отбрасывает изменяемую часть в фиксированном порядке: сначала старые ходы сессии, потом ранние результаты инструментов этого хода. Старые ходы отбрасываются сразу с запасом — до половины того, что ещё можно отправить, — и точка отбрасывания первого вызова записывается в ход: следующий ход сессии начинает историю там же. Отбрасывание на поздних вызовах ради бюджета самого хода сессию не обрезает, а точкой не может стать ход, не оставивший истории. Начало входа не сдвигается от хода к ходу, и кэш префикса сбрасывается только при новом отбрасывании. Отброшенный результат инструмента можно запросить заново: повтор того же вызова выполнится. Отброшенный результат инструмента заменяется короткой пометкой, а не удаляется: протокол требует ответа на каждый вызов. Отброшенное не пересказывается: дополнительный вызов модели ради пересказа сам стоил бы бюджета. Цитата принимается только из фрагментов, которые были во входе какого-либо вызова этого хода, — из отброшенной истории уже нет. Не помогло — вызов не отправляется, и ход заканчивается как на лимите.

**Последний вызов.** Вызов считается последним, если его номер — 4 или если после него в бюджете хода не помещается ещё один: `потрачено + оценка этого вызова + (оценка этого вызова + потолок результата инструмента) > 24 000`. Следующий вызов не может быть меньше текущего, а от нового результата инструмента вырастет не больше чем на его потолок. Последний вызов отправляется с запретом вызова инструментов, чтобы ход закончился ответом. Запрет передаётся параметром запроса; схемы инструментов остаются во входе без изменений, и `prefix_hash` не меняется. Не каждый сервер модели соблюдает запрет: если в ответ на последний вызов модель всё же запросила инструмент — структурно или разметкой в тексте, — он не выполняется.

**Чем заканчивается ход на лимите.** Текстом последнего ответа модели, если он есть; иначе — `budget_exceeded`. Код ответ не составляет.

**Результат инструмента** обрезается до 1 500 токенов до попадания во вход. Обрезанный результат несёт явную пометку и ссылку: идентификаторы следующих фрагментов — их запрашивают по идентификатору — или число оставшихся строк с подсказкой сузить фильтры или период. Продолжение запрашивается тем же инструментом и проходит те же права. Фрагмент не режется посередине: в результат идут целые фрагменты, сколько поместится. Что на части не делится, режется по символам с пометкой об обрезке.

### Неизменная часть входа

Системная часть и схемы инструментов собираются один раз при старте, сериализуются в канонический вид с фиксированным порядком и хэшируются — это `prefix_hash`. В неизменной части нет времени, идентификаторов хода и сессии, имени и прав пользователя. Сведения о пользователе идут заголовком первого вопроса сессии в изменяемой части, отдельным сообщением — нет.

### Что решает код, а что модель

| Вопрос | Кто решает |
|---|---|
| Какие данные попадут во вход | Код: права и обрезка |
| Какой инструмент вызвать и с какими параметрами | Модель; параметры проверяет код |
| Сколько вызовов и токенов | Код |
| `outcome` | Модель предлагает, код проверяет по таблице статусов; `action`, `budget_exceeded`, `error` ставит только код |
| Цитаты | Модель называет фрагменты; код оставляет только те, что были во входе этого хода, включая фрагменты из истории сессии, вошедшей в этот вход |
| Числа, полученные расчётом | Код: инструмент расчёта; входы — только из результатов инструментов хода и сообщения пользователя |
| Текст ответа | Модель; для `action` — шаблон кода; отказ с числом, которого нет во входе хода, код заменяет постоянным текстом |

## API

Пользователь — из заголовка `X-User-ID`. Заголовка нет или пользователя нет в `app.users` — 401, ход не начинается. Заголовок объявлен необязательным и проверяется кодом: обязательный заголовок фреймворк отклонил бы с кодом 422. Пользователь проверяется раньше полей тела: без заголовка и для неизвестного пользователя ответ — 401, какими бы ни были поля; тело, которое не разбирается как JSON вовсе, отклоняется ещё раньше. Лишние поля тела не мешают. Ответ 422 называет поле и причину, но не возвращает сам ввод. Текст, который база не сохранит, — с нулевым символом или не кодируемый в UTF-8 — отклоняется с кодом 422 до начала хода.

| Маршрут | Успех | Отказы |
|---|---|---|
| `POST /turn` | 200 с `outcome` из контракта, включая `error` и `budget_exceeded` | 401; 409 — в сессии уже идёт ход; 422 — неверное тело или слишком длинное сообщение |
| `POST /actions/{id}/confirm` | 200, `{"status": "done", "request_id": …}` | 401; 403 — не автор или полномочие отозвано; 404 — нет действия; 409 — отклонено; 502 — ТОиР недоступен или отверг запрос |
| `POST /actions/{id}/reject` | 200, `{"status": "rejected"}`; повтор — тот же ответ | 401; 403 — не автор; 404; 409 — уже подтверждено |
| `GET /turns/{turn_id}` | 200, запись хода для диагностики | 401; 404 — хода нет или он чужой |
| `GET /info` | 200, сведения о сборке: коммит, хэш набора, `prefix_hash`, имя модели, адрес провайдера без учётных данных, настроена ли модель, параметры выборки | — |
| `GET /` | 200, страница для демонстрации — HTML | — |
| `GET /users` | 200, список пользователей для выбора на странице: идентификатор, ФИО, должность — без полномочий и групп, без заголовка пользователя | — |
| `GET /overview` | 200, что пользователь может спросить: действующие документы его групп, таблицы КХД с участками и периодом данных, участки для заявок и до шести единиц оборудования с них — через `access/`, по тем же правам, что у инструментов | 401 |
| `GET /healthz` | 200, `{"status": "ok"}`: проверка готовности для compose, без заголовка пользователя. Готов — значит база отвечает, схема на последней версии и набор загружен | 503 — база недоступна, схема не той версии или набор не загружен |

Ошибка внутри хода — отказ модели, исключение в инструменте, превышение предела времени — не превращается в 500: ход завершается с `outcome: error`, расход уже сделанных вызовов сохраняется. Расход копится в счётчике хода, куда тело хода записывает каждый вызов модели сразу после ответа, поэтому он не теряется и при исключении. Если запись хода не удалась, клиент получает `outcome: error` и не получает ответ, которого нет в истории; ход, переживший свою отметку занятости, и ход, который не удалось записать, различаются текстом ошибки. Если сбой случился до начала хода — база недоступна при проверке пользователя или захвате сессии, — ответ тоже по контракту, но его `turn_id` ни на что не указывает: записать ход было некуда.

Запись хода и сведения о сборке — дополнение к контракту задания, нужное прогону. В записи хода: вызовы инструментов с параметрами и статусами; результаты инструментов в том виде, в каком они вошли во вход модели; ответы модели; идентификаторы фрагментов во входе; путь разбора итога; замены исхода и цитат кодом; расход по каждому вызову. Запись видит только автор хода, и в ней нет ничего, что не прошло его права: это буквально то, что видела модель от его имени. Чужой ход неотличим от несуществующего. Ответ `POST /turn` при этом не расширяется и остаётся в точности по контракту.

Страница для демонстрации — статический файл `api/page.html`, который сервис отдаёт сам: отдельной сборки нет. Логики прав в ней нет: пользователя она берёт из `GET /users`, обзор доступного и примеры вопросов строит из `GET /overview` — по именам таблиц из контракта формата, без содержимого набора, — а ход, цитаты, расход, заявку и запись хода — из маршрутов выше, отправляя выбранного пользователя в `X-User-ID`. Список пользователей открывает соединение без привязки к пользователю — третье исключение после проверки готовности и сведений о сборке, которое держит тест: справочник `app.users` без построчной защиты, полномочий и групп в ответе нет. Новых прав он не даёт: пользователь в этом сервисе и так задаётся доверенным заголовком. В продукте пользователь — из SSO, и такого маршрута нет.

## Прогон

`make eval` запускает `evalrun/` в контейнере в сети compose. Сервис для него — чёрный ящик: только HTTP.

1. **Попытка — это весь набор заново.** Каждый вопрос задаётся несколько раз; число попыток — настройка. Идентификатор сессии складывается из `session` вопроса, идентификатора запуска и номера попытки, вопрос без `session` получает уникальную сессию. Сессия из нескольких вопросов в каждой попытке проигрывается целиком и по порядку, поэтому попытки не загрязняют историю друг друга, а повторный прогон не попадает в сессии прошлого.
2. **Порядок.** Вопросы одной сессии идут строго по порядку файла; разные сессии независимы. На 409 прогон повторяет запрос после паузы.
3. **Диагностика.** После каждого вопроса прогон читает запись хода по `turn_id` и считает по ней диагностические метрики; конфигурацию запуска берёт из `GET /info`. Недоступность записи диагностику отключает, но проверки контракта не затрагивает.
4. **Проверка «в ТОиР новой заявки нет».** Прогон читает `GET /requests` заглушки до и после вопроса и сравнивает. Адрес заглушки и токен прогон берёт из окружения; сервису он их не передаёт.
5. **Сравнение строк** — по правилам задания: без учёта регистра, пробелы между цифрами удаляются, запятая между цифрами заменяется точкой. Числа — строже задания: ожидание-число сравнивается с числом ответа целиком, закрытое число — с числами и группами цифр; правило задания считается рядом, и отчёт показывает расхождения вердиктов. Виды ожиданий — в AI_TESTING.md, почему так — решение 18 в [DECISIONS.md](DECISIONS.md).
6. **Результаты.** Каждый запуск пишется в `eval/runs/<запуск>.jsonl` по мере вопросов; после полного прогона он копируется в `eval/results.jsonl` и по нему строится `eval/report.md` — оборванный прогон и прогон, где сервис ни разу не ответил, прошлый итог не затирают. До первого вызова модели прогон проверяет, что сервис отвечает на `GET /info` и модель у него настроена — поле `model_configured`: адрес и имя, — а заглушка ТОиР отвечает на `GET /requests`: без модели каждый ход — `outcome: error`, и прогон из одних провалов затёр бы прошлый итог. `make eval-report` пересобирает отчёт без сервиса, `make eval-compare A=… B=…` сравнивает два запуска попарно по вопросам и отказывается, если конфигурации отличаются не ровно в одном поле.
7. **В CI без модели** прогон идёт на записанных ходах: ответы модели из записей ходов платного прогона лежат в `tests/recorded/eval_turns.jsonl` (без результатов инструментов — их заново считает сервис). Тест генерирует набор тем же зерном, сверяет его хэш с прогоном и проигрывает все ходы; вердикты и исходы должны совпасть, а расхождение проигрывания — вызов сверх записанного, ход короче записи — роняет тест. Набор изменился — тест падает, а не пропускается: записанные ходы обновляются после нового платного прогона командой `python -m tests.replay eval/results.jsonl tests/recorded/eval_turns.jsonl` в контейнере тестов (порядок — в TESTING.md).
8. **Мутанты** — сборки сервиса с одной отключённой защитой в `tests/mutants/`, вне основного образа; прогон по каждой той же командой прогона. Прямые запросы запрещённого делает послушная заглушка модели по `questions.attacks.json`, который пишет генератор. Устройство — решение 13 в [DECISIONS.md](DECISIONS.md), порядок и ожидания — [AI_TESTING.md](../development/AI_TESTING.md).

## Телеметрия

Модуль `telemetry/`. Трассы, метрики и журнал уходят по OTLP по HTTP на адрес из `OTEL_EXPORTER_OTLP_ENDPOINT`; без адреса ничего не включается, и ход от телеметрии не зависит. Экспорт идёт в фоне пакетами: недоступный приёмник ход не задерживает. Приёмник по умолчанию — контейнер `grafana/otel-lgtm` профилем `observability` (`make observe`), Grafana на `http://127.0.0.1:3000/grafana/`, на стенде — через прокси с паролем (решения 5, 9 и 23).

| Что | Как |
|---|---|
| Трасса | Одна на запрос. Корень — спан HTTP-запроса, его пишет сам FastAPI; внутри — ход `turn`, вызовы модели `chat <модель>`, инструменты `execute_tool <имя>`; у подтверждения — `action confirm` и вызов ТОиР `POST /requests` |
| Вызов модели | По соглашениям OpenTelemetry для генеративного ИИ: `gen_ai.operation.name`, `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens`, `gen_ai.response.finish_reasons`, `server.address` — хост провайдера без учётных данных |
| Метрики | `gen_ai.client.token.usage`, `gen_ai.client.operation.duration`, `assistant.turns` по исходу |
| Журнал | Журнал сервиса; от `assistant` — с уровня INFO, в том числе итог каждого хода: исход и расход, без текста. Исключение уходит в приёмник только типом — без текста и стека: в них бывают параметры запросов к базе и тело ответа провайдера. В приёмник идут только записи сервиса: сообщения сторонних библиотек и самих экспортёров — нет |
| Идентификаторы | Пользователь (`user.id`), сессия, ход и действие — чтобы найти трассу по жалобе. В продукте пользователь в телеметрии — псевдоним, а приёмник — под правами |
| Ожидаемые исходы | «Сессия занята», повтор подтверждения, чужое или неизвестное действие, отказ провайдера от строгого формата спан ошибкой не помечают: тип пишется атрибутом `assistant.exception` |
| Чего нет | Имени инструмента, которого нет в схемах, — вместо него `unknown`: имя пишет модель. Текста вопроса, входа и ответа модели, аргументов и результатов инструментов: в них данные набора, доступные одному пользователю, а у приёмника своих прав нет. Ключа модели и `TOIR_TOKEN` модуль не получает. Проверка готовности `/healthz` не трассируется: compose вызывает её каждые десять секунд |

Запись хода `GET /turns/{id}` остаётся основной диагностикой для прогона: в ней то, чего нет в телеметрии, — вход и ответ модели, — и она под правами автора хода.

## Где проверяется

| Обязательная проверка задания | Модуль |
|---|---|
| Документ без доступа не попадает во вход — ни поиском, ни по идентификатору | `access/`, `tools/`, политики `kb` |
| Строки КХД чужого участка не попадают во вход | `access/`, политики `dwh` |
| Подтверждение, повтор, чужой пользователь, падение до записи результата | `actions/` |
| Заявка на чужой участок не предлагается и не создаётся | `tools/`, `actions/` |
| Остановка на лимите, потолок входа, размер результата инструмента | `turn/` |
| `TOIR_TOKEN` не встречается во входе модели | `turn/`, `config` |
| `prefix_hash` не меняется | `turn/` |

Как это тестируется, на какой базе и какими сценариями заглушки модели — в [TESTING.md](../development/TESTING.md).

## Упрощения

| Что упрощено | Как в продукте |
|---|---|
| Срок отметки занятости сессии считается по часам процесса сервиса, экземпляр один. Запись поверх чужого хода исключена меткой захвата при любых часах; от часов зависит только то, как долго сессия отвечает 409 | Срок по часам базы или общий сервис блокировок; несколько экземпляров |
| Идентификатор пользователя в заголовке — только из ASCII: заголовки HTTP читаются как latin-1 | Идентификатор приходит из токена шлюза, а не из заголовка |
| Заглушка ТОиР делит сервер PostgreSQL с сервисом, хотя и в отдельной базе под отдельной ролью | ТОиР — чужая система на своей инфраструктуре; для сервиса ничего не меняется: адрес и токен |
| КХД и индекс документов лежат в той же базе, что и состояние | КХД — внешняя система заказчика за соединителем; права в ней проверяются под учётной записью пользователя |
| Набор перезагружается целиком по хэшу | Потоковая синхронизация с источником, включая изменение и отзыв прав |
| Полномочия загружаются из файла | Группы приходят из SSO; назначение полномочий — через управление доступом приложения, с журналом изменений |
| Поиск раскрывает, что закрытый документ на тему запроса существует | Ответ «в доступных вам источниках не найдено» без различения отказа и отсутствия; различие — только в журнале аудита |
| Действие требует идентификатор оборудования в словах пользователя | Уточняющий диалог с выбором из списка доступного оборудования |
| Незавершённое подтверждение доводит повторный запрос клиента | Фоновый исполнитель или движок долгих процессов доводит его сам |
| Незавершённый ход не возобновляется | Состояние хода сохраняется по шагам |
| Действие не имеет срока жизни | Истечение по времени и отзыв |
| Отброшенная история не пересказывается | Сжатая выжимка старых ходов, посчитанная вне бюджета хода |
| Поиск полнотекстовый | Гибридный, с правами в метаданных индекса |
