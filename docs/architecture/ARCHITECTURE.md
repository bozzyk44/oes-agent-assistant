# Архитектура детерминированной части

Всё, что в сервисе не является моделью: процессы, модули, хранение, права, запись, бюджет хода и контракт API. Цель документа — показать, какие гарантии задания держит код и в каком именно месте. Почему выбран стек — в [DECISIONS.md](DECISIONS.md); где это развёрнуто — в [INFRASTRUCTURE.md](INFRASTRUCTURE.md); как проверяется — в [TESTING.md](../development/TESTING.md).

Принцип один: **модель предлагает, код решает.** Модель выбирает инструмент и формулирует ответ. Что она увидит, сколько раз её вызовут, уйдёт ли запись во внешнюю систему и какой `outcome` получит ход — определяет код.

Состав входа, инструменты глазами модели и формат её ответа — в [AGENT.md](AGENT.md). Здесь зафиксирована граница: что код принимает от модели и как проверяет.

## Процессы

```
клиент ──HTTP──> сервис ассистента ──HTTPS──> модель (OpenAI-совместимый API)
 (прогон,          │        │
  страница)        │        └──HTTP + Bearer + Idempotency-Key──> заглушка ТОиР
                   │ роль сервиса                                      │ роль заглушки
                   ▼                                                   ▼
       ┌─ база сервиса <── загрузчик (роль владельца) <── DATA_DIR   база toir ─┐
       └──────────────────────── один сервер PostgreSQL ───────────────────────┘
```

| Процесс | Что делает | Состояние |
|---|---|---|
| Загрузчик | Разовый запуск перед сервисом: роли и базы, миграции, загрузка `DATA_DIR` | Не держит |
| Сервис ассистента | API, права, цикл хода, запись | В PostgreSQL. Сам процесс состояния не держит и перезапускается в любой момент |
| Заглушка ТОиР | Принимает и отдаёт заявки | Своя база `toir` на том же сервере PostgreSQL, своя роль |
| PostgreSQL | Один сервер, две базы: сервиса и заглушки | — |

Сервис подключается к базе под ролью, которая не владеет таблицами и подчиняется построчной защите. Учётных данных владельца у процесса сервиса нет: они есть только у загрузчика.

Движок базы в проекте один. Заглушка ТОиР изображает чужую систему, поэтому изолирована так, как была бы изолирована настоящая: отдельная база, отдельная роль, свой секрет подключения и своя фабрика сессий. Роль сервиса не может подключиться к базе `toir`, роль заглушки — к базе сервиса: право подключения отозвано у всех и выдано поимённо. Сервис знает о ТОиР только адрес и токен и общается с ним только по HTTP.

## Запуск

Одна команда — `make run`. Она создаёт `.env` из `.env.example` со случайными секретами, если файла нет, и выполняет `docker compose up`. Прямой `docker compose up` без `.env` останавливается с сообщением, какой переменной не хватает, а не стартует с пустыми секретами.

На машине нужны только Docker и make. Все цели `make` — `data`, `run`, `test`, `eval` — выполняются в контейнерах; Python на хосте не требуется.

| Шаг | Что происходит | Условие перехода к следующему |
|---|---|---|
| 1. PostgreSQL | Стартует сервер | Отвечает по сети, а не только по локальному сокету: во время инициализации образ поднимает временный сервер, которому верить нельзя |
| 2. Загрузчик | Создаёт роли и базы, если их нет; применяет миграции; загружает набор | Завершился без ошибки |
| 3. Заглушка ТОиР и сервис | Стартуют параллельно | Сервис отвечает на проверку готовности |

Три свойства, от которых зависит запуск на чужой машине:

1. **`DATA_DIR` монтируется в загрузчик с хоста** только на чтение, по умолчанию `./data`. В образ набор не копируется: иначе подмена каталога не подействует.
2. **Роли и базы создаёт загрузчик, а не сценарии инициализации образа PostgreSQL.** Те выполняются только на пустом каталоге данных и недоступны в CI. Шаг загрузчика идемпотентен и работает одинаково локально, в CI и на стенде.
3. **Модель задаётся тремя переменными** — `MODEL_BASE_URL`, `MODEL_API_KEY`, `MODEL_NAME`. Без них сервис стартует, а ход завершается с `outcome: error` и понятной причиной.

## Модули

```
src/assistant/
├── api/        HTTP: маршруты, схемы запросов и ответов, пользователь из заголовка
├── config      настройки из окружения; секрет ТОиР — в отдельном объекте
├── ingest/     проверка формата DATA_DIR и загрузка в базу; запускается загрузчиком
├── access/     права: единственный выход к данным набора
├── tools/      инструменты агента: поиск, документ по ссылке, запрос КХД, расчёт, подготовка заявки
├── turn/       цикл хода: сборка входа, бюджет, неизменная часть, учёт токенов
├── model/      клиент модели за интерфейсом; заглушка для тестов
├── actions/    конечный автомат действия и клиент ТОиР
├── db/         модели SQLAlchemy, миграции Alembic с политиками и функциями
└── telemetry/  трассы и журнал вызовов модели
toir_stub/      заглушка ТОиР, отдельное приложение
datagen/        генератор набора: make data
evalrun/        прогон эталонных вопросов: make eval
```

Правила зависимостей, на которых держатся гарантии:

1. **К данным набора ходит только `access/`.** `tools/` и `turn/` получают данные через него и не обращаются к таблицам набора напрямую. Правило проверяется тестом на импорты.
2. **Секрет ТОиР знает только `actions/`.** `turn/`, `tools/` и `model/` получают настройки без него, поэтому попасть во вход модели ему неоткуда.
3. **`model/` не знает о правах и бюджете.** Он отправляет готовый вход и возвращает ответ с фактическим расходом. Всё, что должно быть проверено, проверено до него.

## Хранение

Три схемы — по тому, чьи это данные в продукте.

| Схема | Что это в продукте | Таблицы | Кто пишет |
|---|---|---|---|
| `kb` | Индекс документов из СЭД | Реестр идентификаторов документов; фрагменты с текстом, полнотекстовым индексом, группами доступа, статусом и ссылками редакций | Загрузчик |
| `dwh` | Внешнее хранилище данных заказчика | `production`, `downtime`, `equipment` — колонки как в CSV | Загрузчик |
| `app` | Собственные данные приложения | Пользователи и их полномочия; сессии, ходы, сообщения, действия; версия набора | Загрузчик — пользователей и полномочия; сервис — состояние |

### Загрузка набора

Загрузчик считает хэш содержимого `DATA_DIR`. Если хэш совпал с записанным в `app` — ничего не делает. Если отличается — одной транзакцией заменяет содержимое `kb`, `dwh`, пользователей и полномочий и очищает сессии, ходы, сообщения и действия.

**Что загрузчик проверяет.** Только то, без чего набор нельзя загрузить: наличие файлов документов, пользователей и трёх таблиц; заголовки и типы колонок CSV; обязательные поля frontmatter; совпадение `id` с именем файла; формат дат и времени. При нарушении загрузчик завершается ошибкой с указанием файла и строки, и сервис не стартует.

**Чего он не проверяет.** Состав набора — число профилей, документов, строк, наличие ловушек — проверяет только генератор в `make data`. Загрузчик принимает любые значения групп, участков, причин простоя и типов оборудования, пропускает неизвестные поля и не читает `questions.jsonl`: файл вопросов в хэш не входит. Набор проверяющих не обязан быть похож на наш ничем, кроме формата.

Два следствия перезагрузки по хэшу:

1. **Подмена набора не оставляет старых данных.** Проверяющий подставляет свой `DATA_DIR` поверх существующего тома базы и получает ответы только по своему набору.
2. **Смена набора — это новая установка.** Сессии очищаются, потому что история хранит данные прежнего набора. Перезапуск с тем же набором состояние сохраняет, включая действия в ожидании подтверждения.

### Пользователи и полномочия

Аутентификация и авторизация разделены. Кто пользователь — сообщает внешний источник: в продукте SSO заказчика, здесь доверенный заголовок `X-User-ID`. Что ему разрешено — хранит приложение.

| Таблица | Что хранит | Источник в `users.json` |
|---|---|---|
| `app.users` | Идентификатор, ФИО, должность | `user_id`, `name`, `position` |
| `app.user_groups` | Группы пользователя для доступа к документам | `groups` |
| `app.kpi_grants` | Пользователь, таблица КХД, участок | `kpi` |
| `app.repair_grants` | Пользователь, участок | `repair_requests` |

`users.json` здесь — способ первичного наполнения этих таблиц, а не то, что сервис читает при каждом запросе. Роль сервиса читает полномочия, но не может их изменить.

### Состояние

| Таблица | Что хранит | Ключевое |
|---|---|---|
| `app.sessions` | Сессия, её владелец, отметка занятости | `session_id` — первичный ключ; `user_id` задаётся при первом ходе и не меняется |
| `app.turns` | Завершённый ход: вопрос, `outcome`, ответ, цитаты, расход | Пишется в конце хода |
| `app.messages` | История сессии для следующих ходов, с идентификаторами фрагментов, которые в ней были | Пишется в конце хода |
| `app.actions` | Предложенное действие и его судьба | Статус, ключ идемпотентности (уникальный), `request_id` |

**Сессия принадлежит одному пользователю.** В истории сессии лежат данные, которые видел её владелец. Ход с чужим `session_id` отклоняется с кодом 403 — иначе второй пользователь унаследовал бы чужой контекст в обход прав.

**Ход атомарен.** Ход, его сообщения и предложенное действие записываются одной транзакцией в конце. До этого в базе от хода есть только отметка занятости сессии. Если узел упал посреди хода, история не содержит половины хода, действие не создано, клиент повторяет запрос. Незавершённый ход не возобновляется.

**Одна сессия — один ход одновременно.** Ход начинается с захвата сессии: условное обновление ставит отметку «занята до» на срок, если сессия свободна или прежний срок истёк. Не удалось — 409. Отметка снимается в завершающей транзакции. У хода есть общий предел времени короче срока отметки, поэтому живой ход не может потерять сессию, а отметка упавшего хода истекает сама и не блокирует сессию навсегда.

## Права

Права держат два независимых барьера. Первый — код: `access/` проверяет полномочия и строит запрос. Второй — база: построчная защита отдаёт роли сервиса только строки, разрешённые текущему пользователю. Ошибка в одном барьере не становится утечкой, пока цел второй.

### Барьер в коде

Объект доступа создаётся на ход из полномочий пользователя в `app` и не меняется до конца хода.

| Запрос | Что делает `access/` |
|---|---|
| Поиск по документам | Условие по группам доступа стоит в самом запросе поиска: ранжируются только разрешённые фрагменты |
| Документ или фрагмент по идентификатору | То же условие. Нет доступа — «доступа нет» без названия, даты и текста |
| Строки таблицы КХД | Нет полномочий на таблицу — «доступа нет», запрос не выполняется. Иначе условие по участкам пользователя добавляется к любому запросу и не снимается параметрами |
| Заявка на ремонт | Участок оборудования берётся из базы, а не из слов модели, и сверяется с `app.repair_grants`. Не совпал — действие не создаётся |

### Барьер в базе

В начале каждой транзакции сервис сообщает базе идентификатор пользователя — параметром с областью действия «до конца транзакции», переданным как значение, а не подстановкой в текст запроса. Участки и группы база берёт из таблиц полномочий сама; сервис не может передать ей расширенный список.

| Таблицы | Политика для роли сервиса |
|---|---|
| `dwh.production`, `dwh.downtime`, `dwh.equipment` | Видна строка, если у текущего пользователя есть полномочие на эту таблицу и участок строки |
| `kb` — фрагменты | Виден фрагмент, если его группы доступа содержат `all` или пересекаются с группами текущего пользователя |
| `app.sessions`, `app.messages` | Видна строка, если сессия принадлежит текущему пользователю |

Параметр не задан или пуст — политики не отдают ни одной строки: забытая привязка к пользователю даёт пустой результат, а не полный. Пустое значение проверяется явно: после первой транзакции на соединении из пула незаданный параметр читается как пустая строка, а не как отсутствие.

Действия и ходы построчной защитой не закрыты: проверку «подтверждает автор» с ответом 403 делает код, и ему для этого нужно видеть чужое действие.

Три выборки намеренно идут мимо политик через функции базы. Каждая возвращает одно значение без содержимого, выполняется с правами владельца, имеет фиксированный путь поиска схем и доступна только роли сервиса.

| Функция | Что возвращает | Зачем |
|---|---|---|
| Существует ли документ | Да или нет по реестру идентификаторов | Отличить «доступа нет» от «не найдено» при запросе по идентификатору |
| Участок оборудования | Код участка | Право на заявку задаётся отдельно от права на таблицу КХД: пользователь может оформлять заявки, не видя таблицы оборудования |
| Есть ли закрытые совпадения | Да или нет: совпал ли запрос с документами, которых пользователь не видит | Отличить «доступа нет» от «не найдено» при поиске |

Третья функция — осознанный компромисс. Задание требует `refusal` на вопрос о документе чужой группы, а отфильтрованный поиск сам по себе вернёт пустую выдачу, неотличимую от отсутствия данных. Функция отвечает одним битом и сужена так, чтобы по ней нельзя было подбирать содержимое: числа в запросе в сравнении не участвуют, а совпадение одного слова признаком не считается. Остаётся возможность узнать, что закрытый документ на некую тему существует, — ровно то, что раскрывает и сам `refusal`.

Результаты функций использует код. Во вход модели попадает только статус инструмента.

### Статусы инструментов и `outcome`

Каждый инструмент возвращает один из статусов. Различие между отказом и отсутствием данных создаёт код, а не догадка модели.

| Статус | Когда |
|---|---|
| `ok` | Данные есть и разрешены |
| `denied` | Документ по идентификатору закрыт. Нет полномочий на таблицу КХД. Все участки, явно названные в запросе, вне полномочий. Поиск ничего не нашёл в доступном, но есть закрытые совпадения. Оборудование на участке без права на заявку |
| `not_found` | Документа или оборудования с таким идентификатором нет |
| `empty` | Запрос разрешён, строк или фрагментов нет |
| `invalid` | Аргументы вызова не прошли схему; на `outcome` не влияет |

Если в запросе к КХД явно названы и разрешённые, и запрещённые участки, инструмент возвращает `ok` по разрешённым и отдельным полем перечисляет участки, в которых отказано. Если участки не названы — считает по всем разрешённым и перечисляет, по каким посчитано: «всего по руднику» от начальника одного участка — это сумма по его участку с явной пометкой, а не число по обоим.

Итоговый `outcome` модель предлагает, код проверяет по статусам этого хода:

| `outcome` | Условие, которое проверяет код |
|---|---|
| `action` | В этом ходе создан черновик действия. Ставит код, модель его не предлагает |
| `refusal` | В этом ходе был статус `denied`. Иначе код заменяет на `no_data` |
| `no_data` | Принимается. Если при этом был `denied`, а в ответе нет ни одной цитаты и ни одного результата `ok` — код заменяет на `refusal` |
| `answer` | Принимается |
| `budget_exceeded`, `error` | Ставит только код |

### Запрос к КХД и расчёты

Инструмент принимает структуру, а не SQL: таблицу, фильтры, группировку и агрегат из закрытых списков. SQL строит код из проверенных частей; модель не может написать условие, которое обойдёт фильтр участка.

| Часть запроса | Что допускается |
|---|---|
| Фильтры | Равенство и вхождение в список по любой колонке; сравнение и диапазон по числам и датам |
| Агрегаты | Сумма, среднее, минимум, максимум, число строк |
| Производные колонки | Моточасы после последнего ППР; длительность простоя в часах |
| Группировка | По любой колонке таблицы и по дате |

Простой попадает в период, если пересекается с ним; в длительность идёт только часть внутри периода. Интервал через полночь при запросе за сутки делится между сутками. Способ расчёта возвращается вместе с результатом.

**Арифметику модель не выполняет.** Проценты, отношения и разности считает отдельный инструмент расчёта: модель передаёт числа из результатов и операцию, код возвращает значение с заданным числом знаков. Сравнение в прогоне идёт по точной строке, и число, посчитанное моделью, — источник случайных провалов.

### Документы и поиск

**Фрагменты.** Документ режется по заголовкам `##`; текст до первого заголовка — отдельный фрагмент. Раздел длиннее потолка делится на части по абзацам и строкам таблиц; потолок — половина лимита результата инструмента, чтобы любой фрагмент помещался во вход целиком. Идентификатор — `<id документа>#<номер раздела>`, у частей длинного раздела добавляется номер части. Название документа и заголовок раздела входят в индекс каждого фрагмента.

**Поиск.** Полнотекстовый, средствами PostgreSQL. Слова запроса приводятся к основе русским стеммером; это стемминг, а не морфологический разбор. Запрос — объединение слов через «или» с ранжированием и отбором лучших: требование всех слов сразу давало бы пустую выдачу на обычный вопрос. Буква «ё» приводится к «е» при индексации и в запросе. Идентификаторы и числа — `EX-03`, `ЭКГ-10` — индексируются отдельно, без стемминга, и ищутся точным совпадением. Векторного поиска нет: он потребовал бы модель эмбеддингов при каждой загрузке чужого набора.

**Редакции.** По умолчанию в выдачу попадают только действующие. Если запрос совпал с утратившей силу редакцией, инструмент возвращает действующую по ссылке `superseded_by` и сообщает, что есть прежняя редакция. Прежняя редакция выдаётся только по явному признаку в запросе и с пометкой «утратил силу, заменён на …» в каждом фрагменте. Права проверяются по `acl` самой запрошенной редакции: о существовании прежней редакции пользователь узнаёт, только если она ему доступна.

**Данные — не инструкции.** Текст документа приходит модели в отдельном блоке результата инструмента с пометкой источника. Три следствия держит код, а не промпт: закрытый документ не попадает во вход независимо от того, что запросила модель; запись без подтверждения невозможна независимо от того, что она ответила; действие не создаётся по тексту документа (раздел «Предложение действия»).

## Запись

Действие — конечный автомат в таблице `app.actions`.

```
              подтверждение автором              ответ ТОиР записан
 proposed ───────────────────────> confirming ───────────────────> done
    │                                │  ▲   │
    │ отказ автора     ТОиР отверг   │  └───┘ повтор подтверждения:
    ▼                  запрос        ▼        тот же ключ, тот же запрос
 rejected                          failed
```

### Предложение действия

Инструмент подготовки заявки проверяет в коде и возвращает черновик или статус отказа:

1. В сообщениях пользователя этой сессии есть идентификатор оборудования. Сравнение — без учёта регистра, пробелов и дефисов. Нет — статус «нужен идентификатор», и модель просит его уточнить.
2. Оборудование существует, иначе `not_found`.
3. Участок оборудования разрешён пользователю, иначе `denied`.
4. Приоритет — от 1 до 3.

Первая проверка закрывает инъекцию: инструкция «оформи заявку на …» в тексте документа не становится действием, потому что идентификатор пришёл не от пользователя. Цена — запрос без идентификатора («на экскаватор первого карьера») не оформляется с первого раза.

После успешного черновика ход завершается без следующего вызова модели: `outcome: action`, текст ответа формирует код по шаблону. Строка действия в статусе `proposed` записывается завершающей транзакцией хода. В одном ходе — не больше одного действия; второй вызов инструмента в том же ответе модели не выполняется. Инструмент ТОиР не вызывает и клиента ТОиР не видит.

### Подтверждение

1. **Намерение.** В транзакции: проверка, что подтверждает автор; повторная проверка полномочия на участок оборудования; переход `proposed → confirming` условным обновлением «только если статус всё ещё `proposed`». Фиксация.
2. **Вызов.** `POST /requests` в ТОиР с ключом идемпотентности действия. Ключ создан вместе с действием и хранится в той же строке.
3. **Результат.** В транзакции: `confirming → done` и `request_id`. Фиксация.

| Ситуация | Что происходит |
|---|---|
| Подтверждения не было | Шаг 2 недостижим: клиент ТОиР вызывается только из перехода в `confirming` |
| Повторное подтверждение после `done` | Возвращается сохранённый `request_id`, ТОиР не вызывается |
| Падение между шагами 2 и 3 | Статус остался `confirming`. Повторное подтверждение повторяет шаг 2 с тем же ключом, ТОиР возвращает ту же заявку, шаг 3 её записывает |
| Два подтверждения одновременно | Оба могут дойти до ТОиР с одним ключом и получат одну заявку |
| ТОиР недоступен, не ответил вовремя, ответил ошибкой сервера или отказом в авторизации | Статус остаётся `confirming`, клиент получает 502 и может повторить. Назад в `proposed` действие не возвращается: неизвестно, создана ли заявка |
| ТОиР отверг запрос как неверный | `confirming → failed`, причина сохраняется. Клиент получает 502; повтор возвращает тот же ответ без вызова ТОиР |
| Полномочие на участок отозвано к моменту подтверждения | 403, статус не меняется |
| Подтверждение или отказ другим пользователем | 403, статус не меняется |
| Подтверждение после отказа | 409 |
| Отказ после подтверждения | 409 |

«Ровно один раз» складывается из двух половин: сервис может вызвать ТОиР больше одного раза, но всегда с одним ключом, а ТОиР по одному ключу создаёт одну заявку. Убрать любую половину — гарантия пропадает, поэтому обе покрыты тестами.

### Заглушка ТОиР

`POST /requests` и `GET /requests` требуют `Authorization: Bearer`. По новому ключу заглушка создаёт заявку, по известному — возвращает прежнюю с тем же идентификатором. Тот же ключ с другим телом — 409.

Уникальность ключа обеспечена ограничением в таблице, а не проверкой в коде. Два одновременных запроса с одним ключом: второй упирается в ограничение, заглушка перехватывает нарушение и возвращает уже созданную заявку, а не ошибку сервера. Схему в базе `toir` заглушка создаёт сама при старте, под своей ролью.

## Ход

```
запрос ─> пользователь ─> захват сессии ─> ┌─ сборка входа ─> оценка ─> проверка бюджета ─┐
                                           │                                               │
                                           └─ результат ≤ 1 500 <── права <── модель <─────┘
                                                         │
                          итог: outcome, цитаты, действие ─> одна транзакция ─> ответ
```

### Бюджет

Проверка стоит перед отправкой, а не после ответа.

| Проверка перед каждым вызовом | Лимит |
|---|---|
| Номер вызова в ходе | не больше 4 |
| Оценка входа этого вызова | не больше 8 000 токенов |
| Фактический вход прошлых вызовов хода плюс оценка этого | не больше 24 000 токенов |

**Оценка токенов.** Счётчик работает без сети и без словаря токенизатора: модель проверяющих неизвестна, а библиотеки точного подсчёта загружают словари из сети при первом вызове. Оценка строится по длине всего запроса — системной части, схем инструментов, сообщений и служебных накладных на каждое сообщение — с консервативным коэффициентом из настроек. После каждого вызова коэффициент сверяется с фактическим входом из ответа провайдера и поправляется только в сторону увеличения оценки. Первый вызов хода состоит из неизменной части и вопроса и далёк от потолка, поэтому поправка успевает сработать до вызовов с результатами инструментов. В `usage` ответа идут только фактические числа.

**Если вход не проходит.** Сборщик отбрасывает изменяемую часть в фиксированном порядке: сначала старые ходы сессии, потом ранние результаты инструментов этого хода. Отброшенное не пересказывается: дополнительный вызов модели ради пересказа сам стоил бы бюджета. Не помогло — вызов не отправляется.

**Последний вызов.** Вызов считается последним, если его номер — 4 или если после него в бюджете хода не останется места ещё на один вызов. Последний вызов отправляется с запретом вызова инструментов, чтобы ход закончился ответом. Запрет передаётся параметром запроса; схемы инструментов остаются во входе без изменений, и `prefix_hash` не меняется. Не каждый сервер модели соблюдает запрет: если в ответ на последний вызов модель всё же запросила инструмент, он не выполняется.

**Чем заканчивается ход на лимите.** Текстом последнего ответа модели, если он есть; иначе — `budget_exceeded`. Код ответ не составляет.

**Результат инструмента** обрезается до 1 500 токенов до попадания во вход. Обрезанный результат несёт явную пометку и ссылку: идентификаторы следующих фрагментов или число оставшихся строк. Продолжение запрашивается тем же инструментом и проходит те же права.

### Неизменная часть входа

Системная часть и схемы инструментов собираются один раз при старте, сериализуются в канонический вид с фиксированным порядком и хэшируются — это `prefix_hash`. В неизменной части нет времени, идентификаторов хода и сессии, имени и прав пользователя. Сведения о пользователе идут первым сообщением изменяемой части.

### Что решает код, а что модель

| Вопрос | Кто решает |
|---|---|
| Какие данные попадут во вход | Код: права и обрезка |
| Какой инструмент вызвать и с какими параметрами | Модель; параметры проверяет код |
| Сколько вызовов и токенов | Код |
| `outcome` | Модель предлагает, код проверяет по таблице статусов; `action`, `budget_exceeded`, `error` ставит только код |
| Цитаты | Модель называет фрагменты; код оставляет только те, что были во входе этого хода, включая фрагменты из истории сессии, вошедшей в этот вход |
| Числа, полученные расчётом | Код: инструмент расчёта |
| Текст ответа | Модель; для `action` — шаблон кода |

## API

Пользователь — из заголовка `X-User-ID`. Заголовка нет или пользователя нет в `app.users` — 401, ход не начинается. Заголовок объявлен необязательным и проверяется кодом: обязательный заголовок фреймворк отклонил бы с кодом 422.

| Маршрут | Успех | Отказы |
|---|---|---|
| `POST /turn` | 200 с `outcome` из контракта, включая `error` и `budget_exceeded` | 401; 403 — чужая сессия; 409 — в сессии уже идёт ход; 422 — неверное тело |
| `POST /actions/{id}/confirm` | 200, `{"status": "done", "request_id": …}` | 401; 403 — не автор или полномочие отозвано; 404 — нет действия; 409 — отклонено; 502 — ТОиР недоступен или отверг запрос |
| `POST /actions/{id}/reject` | 200, `{"status": "rejected"}`; повтор — тот же ответ | 401; 403 — не автор; 404; 409 — уже подтверждено |

Ошибка внутри хода — отказ модели, исключение в инструменте, превышение предела времени — не превращается в 500: ход завершается с `outcome: error`, расход уже сделанных вызовов сохраняется.

Страница для демонстрации — статический файл, который сервис отдаёт сам. Логики прав в ней нет: она показывает только то, что вернул API.

## Прогон

`make eval` запускает `evalrun/` в контейнере в сети compose. Сервис для него — чёрный ящик: только HTTP.

1. **Сессии не пересекаются между запусками.** К значению `session` из вопроса добавляется идентификатор запуска; вопрос без `session` получает уникальную сессию. Повторный прогон и прогон на закрытом наборе не попадают в историю прошлых.
2. **Порядок.** Вопросы одной сессии идут строго по порядку файла; разные сессии независимы.
3. **Проверка «в ТОиР новой заявки нет».** Прогон читает `GET /requests` заглушки до и после вопроса и сравнивает. Адрес заглушки и токен прогон берёт из окружения; сервису он их не передаёт.
4. **Сравнение строк** — по правилам задания: без учёта регистра, пробелы между цифрами удаляются, запятая между цифрами заменяется точкой.

## Где проверяется

| Обязательная проверка задания | Модуль |
|---|---|
| Документ без доступа не попадает во вход — ни поиском, ни по идентификатору | `access/`, `tools/`, политики `kb` |
| Строки КХД чужого участка не попадают во вход | `access/`, политики `dwh` |
| Подтверждение, повтор, чужой пользователь, падение до записи результата | `actions/` |
| Заявка на чужой участок не предлагается и не создаётся | `tools/`, `actions/` |
| Остановка на лимите, потолок входа, размер результата инструмента | `turn/` |
| `TOIR_TOKEN` не встречается во входе модели | `turn/`, `config` |
| `prefix_hash` не меняется | `turn/` |

## Упрощения

| Что упрощено | Как в продукте |
|---|---|
| Заглушка ТОиР делит сервер PostgreSQL с сервисом, хотя и в отдельной базе под отдельной ролью | ТОиР — чужая система на своей инфраструктуре; для сервиса ничего не меняется: адрес и токен |
| КХД и индекс документов лежат в той же базе, что и состояние | КХД — внешняя система заказчика за соединителем; права в ней проверяются под учётной записью пользователя |
| Набор перезагружается целиком по хэшу | Потоковая синхронизация с источником, включая изменение и отзыв прав |
| Полномочия загружаются из файла | Группы приходят из SSO; назначение полномочий — через управление доступом приложения, с журналом изменений |
| Поиск раскрывает, что закрытый документ на тему запроса существует | Ответ «в доступных вам источниках не найдено» без различения отказа и отсутствия; различие — только в журнале аудита |
| Действие требует идентификатор оборудования в словах пользователя | Уточняющий диалог с выбором из списка доступного оборудования |
| Незавершённое подтверждение доводит повторный запрос клиента | Фоновый исполнитель или движок долгих процессов доводит его сам |
| Незавершённый ход не возобновляется | Состояние хода сохраняется по шагам |
| Действие не имеет срока жизни | Истечение по времени и отзыв |
| Отброшенная история не пересказывается | Сжатая выжимка старых ходов, посчитанная вне бюджета хода |
| Поиск полнотекстовый | Гибридный, с правами в метаданных индекса |
