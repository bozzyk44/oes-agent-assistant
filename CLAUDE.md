# CLAUDE.md

Тестовое задание на позицию Tech Lead (корпоративные ИИ-агенты): ассистент сотрудника вымышленного рудника АО «Северная руда». Агент на LLM ищет по документам, запрашивает КХД и готовит заявку на ремонт в ТОиР.

Полный текст задания — [docs/business/TASK.md](docs/business/TASK.md). Это источник истины: при любом сомнении в формате или поведении сверяйся с ним, а не с этим файлом.

## Документы

Все документы, кроме корневых `README.md` и `CLAUDE.md`, лежат в `docs/` по направлениям. В корень и в каталоги с кодом документы не кладём.

| Каталог | Что внутри |
|---|---|
| `docs/business/` | Задание (`TASK.md`), требования, контекст заказчика |
| `docs/architecture/` | `DESIGN.md` (сдаётся, до 3 стр.), `DECISIONS.md` — журнал решений, `ARCHITECTURE.md` — модули, права, запись, бюджет хода, API, `AGENT.md` — состав входа, инструменты и формат ответа модели, `RETRIEVAL.md` — почему поиск без векторов, когда и как их добавлять, что измерять, `INFRASTRUCTURE.md` — состав стенда и лимиты |
| `docs/development/` | `TESTING.md` — тесты детерминированной части, `AI_TESTING.md` — прогон, сравнение вариантов, LLM-судья, мутанты, `EVAL.md` (сдаётся), `JOURNAL.md` — время и пойманные ошибки ИИ, `STAND.md` — как создать и удалить стенд в облаке |
| `docs/planning/` | `PLAN.md` (сдаётся, до 2 стр.), планы работ |

Новое направление — новый подкаталог в `docs/`. `README.md` остаётся в корне и ссылается на сдаваемые документы: проверяющий должен найти `EVAL.md`, `DESIGN.md` и `PLAN.md` с первого экрана. `eval/report.md` и `eval/results.jsonl` — выход прогона по контракту задания, не документы, остаются в `eval/`.

## Состояние

Кода ещё нет. Стек выбран, обоснования — в [docs/architecture/DECISIONS.md](docs/architecture/DECISIONS.md):

- Python, FastAPI; PostgreSQL, SQLAlchemy, Alembic.
- Набор из `DATA_DIR`, пользователи и полномочия загружаются в PostgreSQL отдельным шагом перед сервисом; при смене набора — перезагрузка по хэшу и очистка сессий. Сервис читает данные только из базы.
- Права держат два барьера: слой `access/` в коде и построчная защита базы. Сервис ходит в базу под ролью без владения таблицами; учётные данные владельца есть только у загрузчика.
- Тесты идут на PostgreSQL в локальном контейнере, не на SQLite.
- Движок базы один — PostgreSQL; SQLite и других хранилищ не добавляем. Заглушка ТОиР — отдельная база `toir` и отдельная роль на том же сервере; сервис к этой базе не подключается и ходит в заглушку только по HTTP.
- Агентный цикл — свой, поверх `openai` SDK и Pydantic. LangChain, LangGraph и PydanticAI не подключаем.
- Развёртывание сервиса на стенд и наблюдаемость — после того, как работают четыре правила; наблюдаемость отдельным профилем compose. Базовый `docker compose up` обязан работать локально без облака. Сам сервер стенда описан в `infra/terraform/` и создаётся отдельно от сервиса.

- Хостинг: один сервер в Cloud.ru Evolution, конфигурация `lowcost10-2-4`, создаётся через Terraform провайдером `cloudru/cloud`. Модель — через ИИ-роутер Selectel (`https://api.selectel.ru/aig/v1`). Основная модель первого прогона — `google/gemma-4-31b-it`; для сравнения — `deepseek/deepseek-v4.1-flash` и `qwen/qwen3.8-flash`. Имя модели — только в окружении, не в коде.
- Поиск по документам — полнотекстовый в PostgreSQL. Эмбеддинги, векторный индекс, реранкер и переписывание запроса не добавляются без записи в `DECISIONS.md`; условие пересмотра — в `RETRIEVAL.md`.
- Наблюдаемость на стенде — один контейнер `grafana/otel-lgtm` отдельным профилем compose; отдельные Loki, Tempo, Mimir и Grafana не разворачиваем.
- Трассировка — OpenTelemetry в LGTM, спаны вызовов модели по соглашениям для генеративного ИИ. Langfuse не ставим; адрес приёмника трасс — переменная окружения.

## Лимиты инфраструктуры

Полная таблица — в [docs/architecture/INFRASTRUCTURE.md](docs/architecture/INFRASTRUCTURE.md). Не выходи за них без нового решения в `DECISIONS.md`.

- Один сервер: 2 vCPU с гарантированной долей 10 %, 4 ГБ RAM, сетевой SSD-диск 30 ГБ. Один публичный IP.
- Ноль дополнительных томов, GPU, управляемых баз, балансировщиков и вторых серверов. Не хватает памяти — отключается профиль LGTM, сервер не растёт.
- Ничего невосстановимого на сервере не храним: его можно удалить и создать заново одной командой.
- Сервер стоит около 1 100 ₽ в месяц по калькулятору провайдера; на счёте есть бонусы, но бесплатным его не считай: каждое создание сервера — платное действие.
- Наружу открыт только SSH. Порт сервиса на стенде по умолчанию закрыт и открывается для заданных адресов: у сервиса нет аутентификации. PostgreSQL, заглушка ТОиР и наблюдаемость порты наружу не публикуют — Docker обходит экран на сервере, и защищает только группа безопасности облака.
- **Платные действия — только после подтверждения пользователя:** создание и изменение серверов, дисков, адресов и любых других ресурсов в Cloud.ru и Selectel. Чтение API (цены, конфигурации, списки) подтверждения не требует.
- Секреты (`MODEL_API_KEY`, `TOIR_TOKEN`, пароли базы, `CLOUD_RU_KEY_SECRET`) — только в `.env`; в вывод команд, код и документы не попадают.

Как устроен код — в [docs/architecture/ARCHITECTURE.md](docs/architecture/ARCHITECTURE.md): модули и правила зависимостей, схема базы, автомат действия, проверки бюджета, коды ответов API. Код пишется по этому документу; расхождение исправляется в документе или в коде в том же PR, а не остаётся.

Что видит модель — в [docs/architecture/AGENT.md](docs/architecture/AGENT.md). Системное сообщение и схемы инструментов не содержат ничего из набора данных и ничего переменного; имя инструмента `create_repair_request` и его параметры заданы заданием и не переименовываются.

## Инструменты разработки

- Python 3.14 в контейнере; на хосте Python не нужен.
- Зависимости — `uv` с зафиксированным файлом блокировки.
- `ruff` — линтер и форматирование; `mypy` в строгом режиме на `src/`; `pytest`.
- Новая зависимость — только если без неё не обойтись, и с одной строкой в описании PR, зачем она.

Как проверяется — в [docs/development/TESTING.md](docs/development/TESTING.md). Главные правила оттуда:

- Тесты прав смотрят на вход, записанный заглушкой модели, а не на текст ответа.
- У каждой строки таблиц гарантий в `ARCHITECTURE.md` есть тест с тем же названием. Меняешь таблицу — меняешь тест, и наоборот.
- Тесты не знают содержимого `data/`: свой маленький набор плюс инварианты, которые проходят на любом наборе.
- Без пауз по времени: часы и генератор идентификаторов подставляются.

Как измеряется поведение с настоящей моделью — в [docs/development/AI_TESTING.md](docs/development/AI_TESTING.md). Главные правила оттуда:

- Прошёл вопрос или нет, решают только точные проверки из задания. LLM-судья — дополнение и ничего не блокирует; утечки, числа и `outcome` ему не доверяются.
- Провал не чинится вписыванием в промпт или код чего-либо из набора: названий документов, идентификаторов, чисел.
- PR, меняющий системную часть, инструменты, поиск или модель, идёт с прогоном; результаты кладутся в `eval/` в том же PR. Утечка в любой попытке — слияние запрещено.
- Отключение защиты для проверки набора — только отдельной сборкой рядом с тестами. Флага окружения, отключающего защиту, в коде сервиса быть не должно.

Новое архитектурное решение или смена прежнего — новая запись в `DECISIONS.md`. Когда появится код — допиши сюда команды и структуру каталогов.

## Что сдаём

1. Генератор данных (`make data`) и готовый `data/` в репозитории.
2. Сервис на Python: `POST /turn`, `POST /actions/{id}/confirm`, `POST /actions/{id}/reject`.
3. Заглушка ТОиР отдельным процессом: `POST /requests`, `GET /requests`.
4. Прогон эталонных вопросов (`make eval`) → `eval/results.jsonl`, `eval/report.md`.
5. Тесты без модели и сети (`make test`).
6. `README.md` в корне; `EVAL.md`, `DESIGN.md` (до 3 стр.), `PLAN.md` (до 2 стр.) — в `docs/`, см. раздел «Документы». `DESIGN.md` и `PLAN.md` обязательны при любом раскладе.

## Команды (контракт задания)

| Команда | Что делает |
|---|---|
| `make data` | Пишет набор в `data/` без сети и модели, с фиксированным seed; проверяет формат и состав, падает при нарушении |
| `make run` | Создаёт `.env` из `.env.example`, если его нет, и поднимает PostgreSQL, загрузчик, сервис и заглушку ТОиР |
| `make test` | Линтер, типы и тесты без сети и модели; PostgreSQL поднимается в контейнере, модель заменена заглушкой со сценарием |
| `make eval QUESTIONS=<путь>` | Прогон по запущенному сервису; по умолчанию `$DATA_DIR/questions.jsonl` |

Все цели выполняются в контейнерах: на машине нужны только Docker и make.

Переменные окружения из задания: `DATA_DIR` (по умолчанию `data/`), `MODEL_BASE_URL`, `MODEL_API_KEY`, `MODEL_NAME`, `TOIR_TOKEN`, `PRICE_INPUT`, `PRICE_CACHED`, `PRICE_OUTPUT`.

Свои: `POSTGRES_PASSWORD` (администратор сервера, только загрузчик), `DATABASE_OWNER_URL` (владелец, только загрузчик), `DATABASE_URL` (роль сервиса), `TOIR_DATABASE_URL` (роль заглушки; у заглушки и у загрузчика, который создаёт эту роль), `TOIR_URL`, `OTEL_EXPORTER_OTLP_ENDPOINT`. Для стенда: `CLOUD_RU_KEY_ID`, `CLOUD_RU_KEY_SECRET`, `CLOUD_RU_PROJECT_ID`, `STAND_SSH_PUBLIC_KEY_FILE` — только у Terraform; сервису они не нужны и на сервер не копируются. Каждая новая переменная добавляется в `.env.example`.

## Четыре правила — проверяются кодом, не промптом

1. **Права.** Фильтрация по `acl` документов и по участкам КХД — в коде слоя доступа, до попадания данных в контекст модели; построчная защита базы — второй барьер, а не замена первому. Это относится и к поиску, и к запросу по прямому id, и к явному запросу чужих строк. Промпт механизмом прав не считается.
2. **Бюджет.** Не больше 4 вызовов модели на ход; вход одного вызова ≤ 8 000 токенов; вход всех вызовов хода ≤ 24 000; результат инструмента в контексте ≤ 1 500 токенов. Лимит соблюдается при сборке входа: вызов, который его превысит, не отправляется. Оценка до вызова — локальным счётчиком с запасом, без сети и без словаря токенизатора; в `usage` — фактические числа провайдера.
3. **Запись.** Заявка в ТОиР — только после подтверждения автором и ровно один раз, включая повтор и рестарт между вызовом ТОиР и записью результата (`Idempotency-Key`, состояние действия переживает рестарт).
4. **Измеримость.** Качество, утечки и стоимость — прогоном по `questions.jsonl`.

## Инварианты, которые легко сломать

- **Код не знает содержимого набора.** Никаких id документов, пользователей, оборудования и чисел из `data/` в коде сервиса: проверяющие запустят сервис на своём наборе того же формата. Формат из задания — контракт, отступление = сервис не заработает.
- **Неизменная часть входа стабильна.** Системная часть и схемы инструментов одинаковы во всех вызовах сессии: без времени, id хода, имени пользователя и нестабильного порядка инструментов. `prefix_hash` не меняется между вызовами и ходами.
- **`TOIR_TOKEN`** не попадает во вход модели, в ответы API и в логи вызовов модели.
- **Данные — не инструкции.** Текст документов и результатов инструментов не меняет поведение агента; в наборе есть документ с инъекцией.
- **Редакции.** Ответ опирается на `status: active`; `superseded` упоминается только как история.
- **Числа в эталоне вычисляет генератор.** `must_include`, `forbidden`, `action.params` — из тех же параметров или готовых файлов. Вписанное руками или моделью число — ошибка.
- **`forbidden` не должны встречаться** в документах и строках КХД, доступных автору вопроса, — `make data` это проверяет, иначе прогон покажет ложную утечку.
- **Сравнение строк в прогоне:** без учёта регистра; пробелы между цифрами удаляются, запятая между цифрами → точка.

## Порядок работы

Задание рассчитано на один рабочий день. Если времени не хватает, порядок такой: генератор с пользователями и ловушками прав и записи → права и запись → бюджет → прогон → остальной набор и остальное. Несделанное перечисляется в README.

Модель для основного прогона — открытая, через OpenAI-совместимый API (Qwen, GLM, DeepSeek, Kimi, GigaChat; провайдер или локально).

## Git

В `main` напрямую не коммитим и не пушим. Задачи ведём в GitHub Issues этого репозитория (`gh issue list`); в каждой — результат, критерии приёмки и зависимости. Репозиторий публичный: issue и PR читают проверяющие.

Путь задачи один: issue → ветка в отдельной рабочей копии → PR → проверки → ревью агентом → ревью человека → squash-merge. Порядок действий — в скиллах проекта, не воспроизводи его по памяти:

| Скилл | Когда |
|---|---|
| `take-issue` | Взять задачу по номеру и довести до PR |
| `independent-review` | Ревью агентом с чистым контекстом: перед слиянием любого PR и после крупной правки документов |

Что действует независимо от скиллов:

- Нет подходящей задачи — сначала заведи её с критериями приёмки.
- Имя ветки — `<тип>/<номер issue>-<кратко>`; типы — `feat`, `fix`, `docs`, `infra`. Одна ветка — одна задача.
- Одни и те же цели `make` локально и в CI. Красный CI — PR не готов к ревью.
- Находки ревью исправляются новыми коммитами в той же ветке, без переписывания истории.
- Мержит человек. Агент не сливает и не одобряет PR, пока пользователь прямо не сказал слить этот PR.
- Перед каждым коммитом проверь, что в дифф не попали секреты и личные данные.
